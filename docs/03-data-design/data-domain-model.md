# 数据域概念模型

## 1. 目的

本文档为 AI Cinematic Studio 建立技术无关的数据语义分类，用于后续讨论时统一词汇、识别边界并发现跨域责任。它只定义概念分类，不是逻辑或物理数据模型，也不证明任何模块、接口或实现已经存在。

本模型严格包含以下七个数据域：Identity、Project、Asset、Production、Render、Business、Intelligence。数据域名称不等同于 V2.3 模块、服务、仓库目录、部署单元或所有权边界。

## 2. 建模原则

1. 数据域按语义责任分类，不按技术位置、产品页面或组织结构分类。
2. 一个概念归入某域，表示该域对其核心语义具有解释力，不表示该域已经获得权威所有权。
3. 跨域引用不复制权威语义，也不自动转移写入权或治理责任。
4. 派生、聚合或观察结果必须与来源语义区分，不能反向成为来源事实。
5. 具体所有权只能通过独立、获批的所有权记录声明；本文件不作实际分配。
6. 本分类不得被用来推导反向、跨层或循环依赖。

## 3. 概念数据域

| 数据域 | 概念范围 | 边界 | 非目标 |
| --- | --- | --- | --- |
| Identity | 描述身份识别、身份上下文及其治理语义 | 只负责解释“由谁或以何种受治理身份参与”的概念，不吸收其他域的内容语义 | 不定义认证机制、权限模型、凭据、身份记录结构或实现系统 |
| Project | 描述项目范围、项目上下文及其连续性语义 | 只负责解释信息如何归属于一个项目语境，不替代该语境中其他域的权威含义 | 不定义项目业务流程、组织方式、生命周期状态、字段或产品功能 |
| Asset | 描述可识别内容资产及其连续身份语义 | 只负责解释资产作为受识别内容的概念边界，不承担生产过程、渲染执行或商业解释 | 不定义资产类型、格式、版本结构、文件组织、元数据字段或存储位置 |
| Production | 描述内容生产上下文及其过程语义 | 只负责解释生产语境中的意图、进展与结果关系，不接管资产身份或渲染执行语义 | 不定义工作流步骤、任务类型、状态机、产品操作或编排实现 |
| Render | 描述渲染语境及其执行结果语义 | 只负责解释渲染相关意图与结果的概念边界，不定义通用计算资源或资产权威身份 | 不定义渲染引擎、参数、作业结构、文件格式、执行协议或技术栈 |
| Business | 描述商业语境及其解释性语义 | 只负责商业含义，不改变被引用项目、资产、生产或渲染信息的来源语义 | 不定义商业规则、计费模型、订单结构、价格、合同、产品能力或实现流程 |
| Intelligence | 描述由一个或多个域产生的分析、推断与知识性语义 | 必须与来源事实保持可区分和可追溯，不因派生而取得来源域的权威地位 | 不定义指标、模型、特征、算法、训练数据结构、报告或 AI 技术选型 |

表中的描述只用于划定概念语义，不能作为创建业务对象、字段或接口的需求依据。

## 4. 域边界判定

对未来经授权的数据概念进行分类时，应按顺序回答：

1. 需要被权威解释的核心语义是什么？
2. 若移除技术名称、页面名称和流程名称，该语义仍属于哪个数据域？
3. 它表达来源事实、过程上下文、执行结果、商业解释，还是派生理解？
4. 它是否只引用另一域的身份，而没有取得该域的修改权？
5. 是否存在多个域都声称解释同一核心语义的冲突？

无法唯一判断时，应记录待决边界并进入数据治理评审，不得通过复制概念或创建共享存储来规避冲突。

## 5. 交叉关系

七个数据域可以在概念层发生以下关系，但这些关系不构成 API、数据流或实现设计：

| 关系 | 概念说明 | 必须保持的边界 |
| --- | --- | --- |
| Identity 与其他域 | 其他域可以在适用场景中引用身份上下文 | 引用不使 Identity 取得其他域语义，也不使其他域取得身份权威 |
| Project 与 Asset、Production、Business、Intelligence | 项目语境可以为相关概念提供归属上下文 | 项目归属不改变被引用域的核心语义或所有权 |
| Asset 与 Production、Render、Business、Intelligence | 其他域可以引用资产身份来表达各自语境 | 对资产的引用、处理、商业解释或分析不等于修改资产权威事实 |
| Production 与 Render | 生产语境可以与渲染语境建立可追溯关联 | 两者保持独立语义，关系不预设流程、调用方式或执行机制 |
| Business 与其他域 | 商业语境可以引用其他域的已治理语义 | 商业解释不覆盖来源语义，也不反向决定来源事实 |
| Intelligence 与其他域 | Intelligence 可以形成跨域派生理解 | 派生结果必须保留来源可追溯性，并与来源事实明确区分 |

任何交叉关系都必须在后续获批契约中声明来源语义、权威 owner、消费目的和变更影响。关系本身不授权直接写入另一域，也不能绕过 V2.3 的相邻层依赖方向。
所有权声明遵守 [数据所有权](data-ownership.md)，统一 Project ID、Asset ID 等标识继续遵守 [接口契约基础](../04-interface-contract/README.md#5-统一关联标识)；这些标识不构成实体模型或域间基数关系。

## 6. 明确非目标

本文档不定义或列举：

- 业务实体、业务对象或产品功能；
- 属性、字段、枚举、标识符格式或校验规则；
- 表、schema、关系、索引、查询或迁移；
- API、端点、消息、事件、协议或序列化结构；
- 数据库、文件系统、缓存、搜索、分析平台或具体存储；
- 数据在 Application Layer、V5 Core OS、V4 Platform、V3 Render Core 或 Compute 中的实际归属；
- V2.3 模块的新增、删除、拆分、职责调整或依赖变化。

## 7. 变更控制

新增、删除、合并或重命名数据域属于概念基线变更，必须关联独立任务，说明对现有语义、所有权记录、接口契约和依赖边界的影响，并完成数据治理与架构评审。任何数据域变更都不能自行改变 V2.3。
