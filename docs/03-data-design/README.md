# AI Cinematic Studio 数据架构基础

## 1. 目的与范围

本目录建立 AI Cinematic Studio V2.3 的概念数据架构基础，用于统一数据分类、所有权、Asset 生命周期、一致性约束和存储能力术语。

这些文档是治理与设计边界，不是数据库设计。它们不定义业务实体、字段、表、关系、索引、查询、迁移、数据访问代码、物理拓扑或具体产品，也不将逻辑数据域自动映射到 V2.3 的某个层级。

## 3. 数据分类

七类数据域是概念分类标签，不是实体、表、服务或存储容器：

| 数据域 | 概念范围 | 本阶段不定义 |
| --- | --- | --- |
| Identity | 区分主体、身份上下文及其受治理引用所需的数据 | 账号、凭据、权限表或身份产品 |
| Project | 表达项目上下文、范围和关联所需的数据 | Project 实体字段、成员关系或工作流 |
| Asset | 表达资产身份、描述、血缘、版本与生命周期所需的数据 | Asset 类型清单、元数据字段或物理文件结构 |
| Production | 表达生产活动上下文及其可追溯结果所需的数据 | 生产流程、任务实体或状态机实现 |
| Render | 表达渲染上下文、输入输出关联和执行证据所需的数据 | 渲染参数、引擎模型或作业结构 |
| Business | 表达商业与经营事实所需的数据 | 客户、订单、计费等业务实体或规则 |
| Intelligence | 表达从权威数据派生的语义、分析或智能结果所需的数据 | 模型、特征字段、向量格式或推理实现 |

具体资料的主分类、次级关联和边界冲突处理规则见 [数据域模型](data-domain-model.md)。

Project ID、Asset ID、Job ID 等名称继续沿用 [接口契约基础](../04-interface-contract/README.md#5-统一关联标识) 中的不透明关联语义；分类名称和标识名称都不证明相应业务实体、父子关系或持久化模型已经存在。

## 4. 数据所有权

每项未来获批的数据责任范围必须从以下逻辑边界中明确一个权威所有者：

| 任务术语 | V2.3 规范名称 |
| --- | --- |
| Application | Application Layer |
| V5 | V5 Core OS |
| V4 | V4 Platform |
| V3 | V3 Render Core |
| Compute | Compute |

“可以作为所有者”不代表某个数据域已被分配给该层。ACS-P0-004 不猜测七类数据域的实际归属；具体分配必须依据 V2.3 权威架构、关联任务和获批责任记录完成。

Foundation 仍保留在 V2.3 系统上下文中，但不属于本任务列出的数据所有权角色；这既不删除该层，也不为其新增数据职责。

基本规则：

1. 一项权威数据在同一治理范围内只能有一个权威所有者。
2. 只有所有者或其明确授权的公开契约可以接受权威状态变更。
3. 消费方、缓存、索引和分析副本都是派生视图，不能反向成为事实来源。
4. 数据所有权不因物理存储位置、复制、处理层级或团队部署位置而改变。
5. 跨层读写必须经过 [接口契约基础](../04-interface-contract/README.md)，不得共享内部存储形成隐式契约。

## 5. Asset 生命周期

Asset 生命周期只定义可审核的概念阶段与转换条件，不规定数据库状态字段或业务工作流。生命周期必须覆盖身份建立、形成与验证、可用、变更或派生、归档以及受控处置，并持续保存所有权、血缘、版本、保留和审计证据。

Asset ID 只承担稳定身份与关联作用，不编码生命周期状态、存储位置、格式或所有权。完整规则见 [Asset 生命周期](asset-lifecycle.md)。

## 6. 抽象存储能力

| 抽象能力 | 逻辑目的 |
| --- | --- |
| Operational Storage | 支持当前运行状态及受控状态变更 |
| Object Storage | 承载大体量或不透明内容对象及其受控版本 |
| Vector Storage | 承载可重建、具有来源血缘的派生向量表达 |
| Analytics Storage | 承载用于分析的历史、汇总或派生视图 |

这些名称是能力分类，不是产品、部署单元或强制的数据域映射。技术选择必须使用 [技术栈选型记录模板](../../architecture/technology-stack-decision.md) 并按治理流程批准。

Identity、Project、Asset、Production、Render、Business、Intelligence 中的任何分类都不会自动对应某种存储能力；每个未来绑定都必须独立说明必要性、所有权和一致性影响。

## 7. 数据设计声明清单

未来具体数据设计进入评审前，至少应声明：

- 数据分类及分类理由；
- 权威所有者、允许写入方和消费方；
- 权威数据与派生数据的区别；
- Asset 生命周期或其他适用生命周期约束；
- 所需抽象存储能力，而非产品名称；
- 一致性、冲突、版本、血缘和时间语义；
- 敏感性、保留、归档和处置责任；
- 迁移、验证、回滚及审计要求。

该清单是文档评审元数据，不是持久化字段定义。

## 8. Phase 0.4 非目标

本阶段不创建数据库、SQL Schema、业务实体、数据表、字段、索引、外键、迁移、ORM、Repository、查询、数据访问服务或存储产品选型，也不实现 V5/V4/V3/Compute 的业务数据逻辑。
