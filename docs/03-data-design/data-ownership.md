# 数据权威所有权治理

## 1. 目的

本文档规定数据权威所有权的声明方式，用于确保每项经治理的数据责任只有一个可追溯的权威 owner，并明确写入、派生、消费和治理职责。它是技术无关的治理规则，不是数据库、代码、API、产品或模块设计。

本文只提供可声明边界与空白登记模板，不把 Identity、Project、Asset、Production、Render、Business、Intelligence 中的任何数据域实际分配给某一层。
七类语义的定义以 [数据域模型](data-domain-model.md) 为准；跨层读写与标识传播继续遵守 [接口契约基础](../04-interface-contract/README.md)，所有权记录不能替代接口批准。

## 2. 可声明的权威所有权边界

获批的所有权记录可以从以下高层边界中声明一个权威 owner：

| 可声明边界 | 声明含义 | 不代表 |
| --- | --- | --- |
| Application Layer | 经评审后可承担某一明确数据责任范围的权威所有权 | Application Layer 自动拥有面向应用的所有数据 |
| V5 Core OS | 经评审后可承担某一明确数据责任范围的权威所有权 | V5 Core OS 自动拥有 Identity、Project 或任一其他数据域 |
| V4 Platform | 经评审后可承担某一明确数据责任范围的权威所有权 | V4 Platform 自动拥有平台相关或跨层数据 |
| V3 Render Core | 经评审后可承担某一明确数据责任范围的权威所有权 | V3 Render Core 自动拥有 Asset、Production、Render 或其结果 |
| Compute | 经评审后可承担某一明确数据责任范围的权威所有权 | Compute 自动拥有作业、执行、资源或渲染相关数据 |

这些名称只是允许写入登记记录的高层边界，不证明具体实现存在，也不扩展其 V2.3 职责。本任务不对其他层级、模块或目录作所有权推断。

## 3. 单一权威 owner 原则

1. 每个获批的数据责任范围在同一时点必须且只能有一个权威 owner。
2. 权威 owner 负责该范围的语义解释、有效变更、质量责任、生命周期治理及公开契约。
3. 多层消费、缓存、复制、计算或展示同一语义，不会产生第二个权威 owner。
4. 一个数据域可以在未来被划分为多个经评审的责任范围，但每个范围仍必须各自满足单一 owner；本文件不预先进行划分。
5. 跨域关系不允许共同所有权。若边界不清，应先解决语义范围，再批准所有权记录。
6. 所有权转移必须有明确生效条件、迁移验证与回滚方案；在转移完成前不得同时宣称两个权威来源。

## 4. 职责模型

### 4.1 权威所有权职责

权威 owner 必须：

- 维护所登记责任范围的唯一权威语义；
- 明确允许写入和消费的公开边界；
- 对质量目标、变更兼容性和生命周期规则负责；
- 确保来源、变更和派生关系可追溯；
- 对安全、隐私、合规与保留要求发起并维护适用的治理声明；
- 在不改变 V2.3 依赖方向的前提下评审相关契约变更。

### 4.2 写入职责

- 权威 owner 是有效写入规则的最终责任方。
- 其他边界只有在公开契约明确授权时才能提交写入意图；授权不转移所有权。
- 不得通过共享存储、内部实现、脚本或基础设施配置绕过 owner 直接修改权威语义。
- 写入失败、冲突与校验责任必须在具体契约获批时说明；本文件不定义其实现。

### 4.3 派生职责

- 派生结果必须声明来源范围、派生责任边界、可追溯要求和失效条件。
- 每项获批的派生责任范围自身也必须有一个权威 owner，但该 owner 只对派生语义负责。
- 派生结果不得覆盖、回写或冒充来源事实，除非另有获批写入契约。
- Intelligence 的派生性质不使其自动取得任何来源数据域的所有权。

### 4.4 消费职责

- 消费方只通过获批公开契约使用数据，不依赖 owner 的内部表示。
- 消费方负责遵守用途、适用范围、时效和访问治理约束。
- 本地副本、缓存、索引、展示或计算结果不改变来源 owner。
- 消费方不得将观察结果包装为新的权威来源，也不得向上游形成反向依赖。

### 4.5 治理职责

- 权威 owner 对登记信息的完整性、复审和变更证据负责。
- 数据治理评审负责检查单一 owner、边界冲突、派生可追溯性和规则一致性。
- 架构评审负责确认所有权声明不改变 V2.3 模块职责，不产生反向、跨层或循环依赖。
- 具体执行人员和评审人员必须在实例记录中明确，本模板不预先指定团队。

## 6. 登记验收规则

一项所有权声明获批前必须确认：

1. 概念责任范围清晰，且没有列出或隐含未获批的业务实体与结构；
2. 只声明一个权威 owner，不使用“共同拥有”或无法追责的集合名称；
3. 数据域分类与 owner 分别评审，没有从分类名称自动推导层级归属；
4. 写入、派生、消费和治理职责均有明确边界；
5. 与其他记录不存在重叠权威范围，或冲突已在生效前解决；
6. 所有层间交互遵守相邻依赖方向和已批准接口契约；
7. 未定义数据库、schema、API、字段、协议、存储技术或产品行为；
8. 未新增、删除、拆分、重命名或重新分配 V2.3 模块职责。

## 7. 所有权变更与例外

新增、转移、合并、拆分或撤销所有权记录必须关联独立任务，记录原因、影响范围、生效边界、迁移验证、回滚条件和复审证据。临时写入或消费例外不产生所有权，也不得长期替代正式记录。

若所有权提案与 V2.3 层级职责、依赖方向或现有权威记录冲突，应停止实施并进入架构与数据治理联合评审。不得通过本文件或登记模板单方面改变 V2.3。

## 8. 明确非目标

本文档不实际分配七个数据域，不定义业务实体、字段、表、schema、API、事件、协议、数据库、存储、数据迁移、代码、产品流程或具体技术方案。
