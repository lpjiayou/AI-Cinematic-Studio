# AI Cinematic Studio 数据一致性规则

## 1. 文档定位

本文定义 ACS 数据在所有者边界内和架构边界之间必须保持的概念一致性语义，包括权威来源、不变量、跨层契约、派生数据、版本与冲突、幂等语义声明、删除与归档传播、审计及时间语义。

本文只定义正确性结果和责任，不选择强一致性、最终一致性或任何产品机制，不设计分布式事务、数据库、表、Schema、API 或消息系统，不实现任何代码，也不改变 V2.3 架构。

## 2. 规范术语

- **权威所有者**：依据 V2.3 架构对某类数据的定义、有效性和变更规则承担最终责任的已批准边界。
- **单一权威来源**：对某项事实作出最终裁决的唯一逻辑来源，不等同于某个数据库、文件或产品实例。
- **副本**：为读取、传输、缓存、索引、分析或其他获批目的保存的非权威表达。
- **派生数据**：通过可说明的规则从一个或多个来源计算、转换或汇总得到的数据。
- **不变量**：在规定责任范围和可见点上必须始终成立的正确性条件。
- **版本**：用于区分数据事实或契约在时间上不同有效内容的逻辑身份。
- **冲突**：两个或多个候选变化无法在不丢失意图或违反不变量的情况下同时成为权威结果。
- **一致性契约**：所有者与使用方就可见性、版本、冲突、陈旧、修复和失败行为达成的获批语义约定。

上述术语不指定存储模型、字段或技术实现。

## 3. 单一权威来源

### 3.1 基本规则

- 每一项可跨边界使用的数据事实必须有且只有一个逻辑权威所有者。
- 权威所有者负责定义语义、合法变化、不变量、版本规则、可见性承诺和废弃方式。
- 副本、缓存、索引、报表和派生结果不得把自身声明为同一事实的第二权威来源。
- 非所有者不得直接改写权威事实；变更意图必须通过获批契约交由权威所有者裁决。
- 物理位置、离使用方更近、更新时间更晚或响应更快，都不能自动产生权威性。
- 权威所有权变化属于架构敏感变更，必须按 ADR 流程批准，并提供使用方迁移、并行验证和旧权威退出证据。

### 3.2 使用方责任

- 使用方必须知道其读取的是权威事实、副本还是派生结果。
- 对非权威数据作出决策时，必须遵循契约声明的版本、陈旧和失败语义。
- 发现权威事实冲突时不得自行选择“看起来最新”的值覆盖所有者结论。
- 关联标识只帮助定位事实，不能证明数据权威性、所有权或访问权限。

## 4. 所有者边界内的不变量

权威所有者必须明确维护本责任范围内的不变量，并对外说明不变量在哪个可见点成立。最低规则包括：

- 每项不变量必须有稳定描述、适用范围、责任人、违反条件和验证证据。
- 一个变化在被所有者声明为有效前，必须满足所有适用不变量；不能向外暴露一个被宣称有效但已知违反不变量的结果。
- 多项事实共同构成一个不可分割的治理约束时，所有者必须声明整体成功、整体不生效或其他获批的失败语义，但本文不规定事务机制。
- 不变量失败必须显式报告，不能通过默认值、静默截断、自动覆盖或省略错误掩盖。
- 修复历史不一致时必须保留原事实、修复依据、责任、影响范围和生效时间的审计证据。
- 所有者不得把内部不变量的维护责任转嫁给外部使用方，也不得要求使用方依赖内部存储细节。

不变量的具体业务内容不在 Phase 0 定义；本文只规定其治理方式。

## 5. 跨层与跨边界契约

- 数据跨越层级或责任边界前，必须有获批契约定义语义、所有者、必填信息、版本、验证、错误和兼容性规则。
- 跨层契约只能公开使用方完成获准目标所需的信息，不泄露所有者内部模型或存储结构。
- 发送方负责在边界输出前验证契约；接收方负责拒绝无法安全解释的内容，不得猜测缺失语义。
- 契约必须区分“未知”“不存在”“不可披露”“尚未确定”和明确空值，不得用同一默认值混淆。
- 契约必须声明对未知字段、未知版本和部分信息的处理方式。
- 跨层转换必须保留来源语义；无法无损转换时，应显式收敛并记录影响，不能伪造精度。
- 契约变更需评估生产方、接收方、历史数据、副本和派生结果，不能只验证单一实现。

跨层契约规定逻辑结果，不等同于 API、事件、序列化或传输协议设计。
具体契约必须遵守 [接口契约基础](../04-interface-contract/README.md)，错误表达遵守 [错误码标准](../04-interface-contract/error-code-standard.md)；一致性规则不得增加接口或事件字段。

## 6. 派生数据

### 6.1 权威性

- 派生数据默认不是其输入事实的权威来源，除非 V2.3 架构通过正式决策明确赋予不同责任。
- 派生结果必须能定位到直接输入的身份或版本、使用的派生规则版本、形成时间和责任边界。
- 派生结果不得覆盖或静默修正其权威输入。

### 6.2 陈旧与重建

- 派生数据契约必须说明输入变化后该结果何时被视为陈旧、陈旧期间是否允许使用、由谁触发修复及如何验证恢复。
- 若派生过程可重建，必须说明重建所需的权威输入、规则版本和完成判据；“可重建”不能成为不保留必要血缘的理由。
- 无法完整重建时，必须明确额外保留和验证责任。
- 权威事实被纠正、归档或处置时，派生所有者必须按获批传播规则评估并处理受影响结果。

### 6.3 可解释性

派生结果必须能够回答：来源是什么、使用了哪个规则、何时形成、当前是否仍适用、与权威输入是否存在已知差异。本文不规定计算引擎、索引、缓存或存储技术。

## 7. 版本与冲突规则

### 7.1 版本

- 权威事实和跨边界契约必须具备可区分变化先后的逻辑版本语义。
- 版本必须与适用内容绑定，不得因复制、重试、搬迁或重新编码而无依据地形成新语义版本。
- 使用方不得仅依据本地接收时间、物理时间戳或“最后写入”猜测哪个版本权威。
- 历史版本在保留期内必须保持可审计；修正不能静默覆盖曾经生效的事实。
- 版本标识、格式、生成算法和保存方式由后续获批技术契约决定。

### 7.2 冲突

- 一致性契约必须定义什么构成冲突、由谁裁决、裁决前允许什么行为以及如何通知受影响方。
- 冲突不得默认采用最后写入者获胜、任意覆盖、字段拼接或多数副本决定；任何策略都需根据语义显式批准。
- 冲突解决必须优先保护不变量、原始意图和审计证据，不能为了快速收敛丢弃未知变化。
- 自动解决只适用于已证明安全且具备确定性规则的范围；其他冲突必须进入受控裁决。
- 裁决结果必须包含依据、责任、生效时间、被替代版本和受影响副本或派生结果的处理责任。

本文不选择并发控制、锁、共识或版本向量等技术。

## 8. 幂等语义声明

幂等是契约语义，不是对实现的默认假设。每个可能被重复提交或重复观察的受治理操作，必须明确声明其是否幂等；未声明时，使用方不得假设重复执行安全。

幂等声明至少应包含：

| 声明项 | 必须说明的问题 |
| --- | --- |
| 逻辑操作身份 | 哪些重复意图被认定为同一个逻辑操作；身份由谁确立 |
| 适用范围 | 幂等保证适用于哪个责任边界、对象和版本 |
| 效果语义 | 首次成功后再次处理是否产生新的权威变化或外部效果 |
| 结果语义 | 重复处理返回原结果、等价结果还是明确的已处理结论 |
| 时间与生命周期 | 保证是否受时间或生命周期限制；限制条件如何向使用方声明 |
| 并发与冲突 | 同一逻辑操作并发出现时如何判断和裁决，不变量如何保护 |
| 失败边界 | 部分失败、未知结果或恢复后能否安全重试；由谁确认最终结果 |
| 审计 | 如何证明重复被识别以及最终只产生了获准效果 |

- 幂等不能仅通过“使用同一个 ID”宣称成立；必须验证所有受治理效果。
- 幂等也不等同于去重、只处理一次或传输保证。
- 非幂等操作必须明确重复风险、调用方责任和安全恢复方式。
- 本文不规定幂等键字段、存储、缓存、锁或消息处理实现。

## 9. 删除与归档传播

### 9.1 语义区分

- **归档**表示数据退出常规使用但仍按获批保留和访问规则保存。
- **删除或处置**表示在授权范围内终止内容及相关副本的可用性，同时保留最小必要审计证明。
- 归档、删除、访问限制和逻辑不可见不得被混为同一语义。

### 9.2 传播责任

- 权威所有者负责发起并说明归档或处置的对象、版本、依据、生效条件和已知影响范围。
- 副本和派生数据所有者负责声明接收、执行、验证与例外结果，不得把收到意图等同于已经完成。
- 传播范围必须覆盖已知副本、缓存、索引、派生结果、导出物和在途处理责任；无法控制的外部副本必须明确记录边界与补偿措施。
- 有效保全、审计或合规义务存在时，应按获批规则阻止、延迟或限制传播，并记录依据。
- 派生结果是否需要同步归档或处置必须依据其独立义务和血缘评估，不能仅凭父级变化自动猜测。
- 传播完成必须有覆盖范围、未完成项、例外、责任人和验证证据。
- 恢复归档数据时，必须重新评估当前权威版本、契约、访问与派生一致性。

本文不规定墓碑、级联删除、队列、轮询、触发器或数据库级联机制。

## 10. 审计规则

每项影响权威事实、不变量、版本裁决、派生关系、归档或处置的变化都必须具备可追溯证据，至少能够说明：

- 目标事实和适用版本。
- 变更前后语义及生效范围。
- 发起、授权、执行和验证责任。
- 变更原因、依据、关联契约或决策。
- 事件时间、生效时间、记录时间及其差异原因。
- 对副本、派生结果和使用方的影响。
- 冲突、例外、失败、修复和最终结论。

审计证据必须防止未授权改写、遵循最小披露并满足保留规则。具体日志格式、签名、存储和查询技术不在本文范围内。

## 11. 时间语义

契约必须根据适用性明确区分以下逻辑时间：

- **事件时间**：被描述的事实实际发生的时间。
- **生效时间**：该事实按规则开始或停止产生治理效力的时间。
- **记录时间**：权威所有者确认并记录该事实的时间。
- **观察时间**：使用方或副本看到该事实的时间。
- **处理时间**：某个处理活动实际执行的时间。

规则如下：

- 不得用记录时间、观察时间或处理时间静默替代未知的事件时间。
- 时间未知、估算、区间化或由外部声明时，必须显式表达其不确定性和来源。
- 排序和“最新”判断必须依据契约声明的时间与版本语义，不能默认使用本地时钟。
- 时间表达必须无歧义并能说明参考基准；本文不规定物理格式、精度、同步协议或时钟产品。
- 更正时间信息必须保留原值、原因、责任和生效影响，不静默重写历史。
- 跨边界时钟差异和延迟必须被纳入冲突、陈旧与审计判断，不能假定所有时间完全同步。

## 12. 一致性契约最低声明

任何跨边界数据契约必须至少声明以下内容：

1. 权威事实及其唯一所有者。
2. 受保护的不变量和成立的可见点。
3. 版本、历史和兼容性语义。
4. 使用方何时可见变化，以及允许或禁止的陈旧行为。
5. 冲突定义、裁决责任和裁决期间的安全行为。
6. 派生数据的来源、重建和修复责任。
7. 操作的幂等或非幂等语义。
8. 归档、删除、保留和传播完成判据。
9. 失败、未知结果、恢复与验证方式。
10. 审计、时间语义、安全和最小披露要求。

契约应描述可验证结果，不得仅写“强一致”“最终一致”等产品无关但含义不足的标签。具体项目若需要某种一致性保证，必须逐项说明可见性、不变量、陈旧、冲突与恢复语义，再由后续获批设计选择实现方式。

## 13. 偏差、修复与升级

- 检测到不一致时，应首先保护权威事实和审计证据，停止扩大影响。
- 修复责任默认属于产生或维护不一致结果的责任边界，但权威所有者保留最终语义裁决权。
- 修复计划必须说明范围、优先级、使用方影响、验证、回滚和未解决风险。
- 不得通过删除历史、覆盖权威值或关闭检查来让不一致“消失”。
- 涉及所有权、跨层边界、公共契约或 V2.3 架构的变化必须进入 ADR 流程。
- 数据、响应或事件可以按获批契约返回或被观察，但不会因此形成反向、跨层或循环依赖；任何边界都不得通过共享存储直接写入另一所有者的权威数据。
- 高影响或重复出现的不一致应登记治理风险，并跟踪到验证关闭。

## 14. 明确禁止与范围边界

本文不选择、不设计也不实现：

- 强一致性或最终一致性的产品机制。
- 分布式事务、两阶段提交、共识、锁或复制算法。
- 数据库、表、Schema、索引、ORM 或迁移。
- API、事件、消息、队列、缓存、搜索或工作流实现。
- 具体业务不变量、业务数据模型或业务代码。
- V2.3 架构之外的新所有者、模块、服务或依赖关系。

Phase 0 只建立一致性治理规则。任何具体实现与技术选型必须等待后续阶段明确授权。
