# Release 验证流程

## 1. 文档定位

本文定义 AI Cinematic Studio 未来 Release 在进入、执行和完成时必须具备的技术无关验证流程。它规定验证责任、证据和决策，不规定发布工具、部署平台、环境拓扑、测试框架、业务场景或自动化实现。

ACS-P0-005 只建立治理标准，不执行 Release、不创建 Production Validation 测试，也不授权实现任何 V2.3 模块。

## 2. Release 验证原则

1. **候选唯一**：每次决策必须指向一个不可混淆的 Release 候选状态，验证后发生实质变化必须重新评估。
2. **风险驱动**：验证深度依据变更范围、失败影响、可逆性和已知风险确定。
3. **证据先于决策**：没有完整、可追溯证据时不得用主观判断宣称可以发布。
4. **分层不替代**：Production Validation 不能替代 Unit、Contract、Integration 或 E2E。
5. **安全优先**：验证不得使用未授权敏感数据、扩大权限或制造不可控生产影响。
6. **可停止与可回退**：进入 Release 前必须明确暂停、终止和回退条件及责任。
7. **架构不变**：Release 流程不能作为绕过 ADR、接口契约或 V2.3 依赖规则的通道。

## 3. 责任角色

| 角色 | 最低责任 |
| --- | --- |
| Change Owner | 说明变更范围、风险、验证需求、已知限制和恢复方案 |
| Validation Owner | 汇总适用测试证据、确认候选一致并报告缺口 |
| Release Decision Owner | 确认 Gate、批准继续或要求暂停/回退，并保留决策记录 |
| Production Validation Owner | 按批准范围执行发布后验证、监测停止条件并报告结果 |
| Reviewer | 独立检查证据、例外、风险与决策依据 |

具体人员或团队必须在每次 Release 记录中明确；本文不预设组织结构。

## 4. Release 输入条件

进入验证流程前至少需要：

- Release 候选标识及其不可混淆的内容范围；
- 关联任务、架构决策、接口契约和数据治理变更；
- 风险评估及适用的测试层级说明；
- Unit、Contract、Integration、E2E 的适用证据或获批 N/A 理由；
- 当前阶段适用的 [验证 Gate](verification-gates.md) 结论和所有阻塞项状态；
- 未解决缺陷、限制、例外和残余风险；
- 目标环境前置条件与访问责任；
- Production Validation 范围、观察指标、停止条件和完成判据；
- 暂停、恢复及回退计划和责任人。

输入不完整时，Release 状态必须保持暂停，不能先执行后补证据。

## 5. 验证流程

### 5.1 候选冻结与范围核对

1. 确认候选内容、配置和关联文档处于同一可识别状态。
2. 核对实际范围与获批任务一致，没有夹带未评审变更。
3. 识别架构、接口、数据、安全、可观测性和恢复影响。
4. 候选发生实质变化时，标记既有证据是否仍适用并重新执行受影响验证。

### 5.2 分层证据核验

1. 对照 [测试层级](test-levels.md) 确认每类风险由适当层级覆盖。
2. 按 [测试证据标准](test-evidence-standard.md) 检查证据身份、范围、结果和限制。
3. 确认失败、阻塞、跳过和 N/A 均有明确处理结论。
4. 确认 Contract 证据覆盖受影响的公开接口、事件、错误或数据语义。
5. 确认 Integration 与 E2E 证据来自受控且与候选相符的验证边界。

### 5.3 发布前决策

Release Decision Owner 只能作出以下结论：

| 结论 | 含义 |
| --- | --- |
| Proceed | 所有强制 Gate 通过，残余风险和 Production Validation 计划已明确 |
| Hold | 证据、环境、批准或风险处理不充分，禁止继续 |
| Exception Approved | 存在经正式批准、限时且具备补偿控制的例外；例外不得覆盖安全或架构阻塞项 |

每次结论必须记录责任人、时间、证据索引、残余风险和适用条件。
Gate 通过只是 Release 的必要输入，不能替代 Release Decision Owner 的明确授权，也不能追认未经批准的架构、范围或技术变更。

### 5.4 执行期间验证

执行期间只验证候选身份、步骤完成情况、环境响应和预先声明的停止条件。发现以下任一情况必须暂停并升级：

- 实际候选与已验证候选不一致；
- 出现未评估的架构、接口、数据或安全影响；
- 关键观察信号缺失或无法解释；
- 回退能力不再可信；
- 任何强制 Gate 结论失效。

本文不定义部署步骤或自动化机制。

### 5.5 Production Validation

发布后验证只在预先批准的范围内确认：

- 目标环境正在运行预期 Release 候选；
- 关键技术健康信号可用且没有触发停止条件；
- 受影响公开契约仍满足已验证的兼容性预期；
- 错误、追踪和审计关联能够支持问题定位；
- 没有观察到超出已知范围的数据、安全或依赖异常；
- 暂停、回退或进一步观察的判断依据充分。

Production Validation 不得：

- 把真实用户流量当作未评审测试输入；
- 创建未经授权的业务数据或不可逆副作用；
- 读取、复制或暴露超出验证所需的敏感信息；
- 借验证直接修改内部状态或绕过公开契约；
- 用“生产观察正常”替代发布前测试证据。

### 5.6 关闭、继续观察或回退

Production Validation 后必须记录以下结论之一：

| 结论 | 必需动作 |
| --- | --- |
| Validated | 完成判据满足，记录证据、残余风险和后续观察责任 |
| Observation Extended | 证据尚不足但未触发回退条件，明确新增观察范围、期限和责任人 |
| Rollback Required | 触发回退条件，停止扩大影响并执行已批准恢复流程 |
| Incident Escalated | 出现超出 Release 流程处理范围的问题，进入相应事件治理流程 |

“Observation Extended”不能无限期替代完成结论，到期时必须重新决策。

## 6. Release 证据包

Release 关闭前应形成统一证据索引，至少包括：

- 候选身份与范围；
- 风险评估和适用层级；
- 分层测试证据及其结果；
- Gate 与例外决定；
- 执行期间记录；
- Production Validation 结果；
- 缺陷、事件、回退或后续观察事项；
- 最终结论、责任人和时间。

证据必须遵守最小披露，不包含凭据、真实敏感数据或无关内部细节。

## 7. 紧急 Release

紧急性可以缩短等待时间，但不能取消候选身份、风险评估、关键证据、安全/架构阻塞检查、回退准备或 Production Validation。被延后的非阻塞证据必须有批准人、补偿控制、完成期限和跟踪事项。

## 8. Phase 0.5 边界

本流程不执行发布、不创建环境、不编写测试或部署代码、不引入框架与依赖、不定义业务验证场景，也不新增、修改或实现 V2.3 模块及其部署架构。
