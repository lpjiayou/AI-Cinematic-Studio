# AI Cinematic Studio 阶段验证 Gate

## 1. 文档定位

本文定义 Phase 0、Phase 1 与 Phase 2 的最低验证 Gate，用于判断一个阶段是否具备退出条件。Gate 只约束范围、进入条件、必需证据、阻塞条件和退出决定，不定义或推演任何阶段的业务内容。

本文不声称持续集成系统、测试框架、共享环境、自动化流水线或产品实现已经存在。证据可以来自经审查的人工验证或未来获批的自动化能力，但必须按 [测试证据标准](test-evidence-standard.md) 记录。本文不实现测试、代码或环境，不改变 V2.3 架构。

## 2. Gate 基本原则

- **授权先于验证**：Gate 验证已获批范围，不能以通过 Gate 为未授权工作补充授权。
- **证据先于结论**：阶段名称、完成声明或口头确认不能替代可复核证据。
- **最低门槛不可削弱**：阶段或工作项可以增加验证要求，不得低于本文最低要求。
- **风险匹配**：证据深度与影响、不可逆性、安全和架构风险相称。
- **事实与能力分离**：只有实际执行并保留证据的检查才能计入；不得假定某个框架、环境或流程存在。
- **例外可审计**：`N/A`、延期和例外必须有适用依据、责任人和明确批准，不能用于规避强制门禁。
- **阶段独立授权**：通过某阶段 Gate 只允许结束该阶段，不自动授权进入或实现下一阶段内容。

## 3. Gate 角色

### 阶段负责人

- 确认待验证范围与已批准阶段目标一致。
- 指定证据责任人、评审人和最终退出决定人。
- 确保阻塞条件被显式处理，不以进度压力替代门禁。

### 证据责任人

- 形成真实、完整、可复现的验证记录。
- 关联工作项、验收标准、目标版本、验证上下文和实际结果。
- 不得把未运行、受阻或不适用的检查记录为通过。

### 证据评审人

- 独立核对证据完整性、适用性、可追溯性和状态结论。
- 确认 `N/A` 理由、限制、例外和残余风险已得到适当批准。
- 高风险变更应由与证据执行责任分离的合格人员评审。

### 退出决定人

- 根据 Gate 规则作出正式退出决定。
- 项目负责人承担最终阶段退出责任；涉及架构、安全或其他专项边界时，必须同时取得对应责任人批准。
- 角色尚未指定时由项目负责人书面指定，不得由交付作者自行假设权限。

## 4. 通用进入条件

任何阶段 Gate 开始前必须满足：

1. 阶段范围、工作项、验收标准和明确不在范围内事项已有书面批准。
2. 待验证交付物及其版本或修订边界已经冻结，后续实质变化将触发重新验证。
3. 适用的架构、治理、接口和数据规则已识别；架构敏感变更已有 Accepted ADR。
4. 验证计划说明证据项、责任人、预期结果、上下文、风险与 `N/A` 候选。
5. 已知缺陷、限制、风险和例外已登记，不存在被隐瞒的范围缺口。
6. 所需验证上下文确实可用；若不存在相应环境、工具或数据，必须如实记录为 `BLOCKED` 或调整已批准计划，不能声称已经执行。

通用进入条件不满足时，Gate 不得开始，整体决定为“暂停待决”。

## 5. Phase 0 最低验证 Gate

### 5.1 范围

Phase 0 Gate 仅验证已获批的工程仓库基础、目录与文档结构、架构治理规则、测试治理基础及其他明确列入 Phase 0 的非业务交付物。

本 Gate 不验证或授权业务功能、服务实现、数据库设计、生产环境、产品行为或未来模块。Phase 0 标签不能成为预建后续能力的依据。

### 5.2 进入条件

除第 4 节通用条件外，必须确认：

- Phase 0 交付清单和禁止事项已经明确。
- 仓库基础变更已完成作者自检，待验证文件范围稳定。
- 相关治理文档之间的权威关系和交叉引用可识别。
- 没有把不存在的工具链、CI、框架或环境列为已具备能力。

### 5.3 必需证据

- **范围证据**：实际新增或修改资产清单，与获批 Phase 0 任务逐项对应。
- **结构证据**：要求的目录和文件存在、命名正确且非空占位的验证记录；允许空目录时应说明治理用途。
- **内容证据**：必填章节、术语、边界和禁止事项完整的审查记录。
- **一致性证据**：README、架构、治理、数据、接口与测试文档之间无已知矛盾或失效引用。
- **污染检查证据**：没有业务代码、服务实现、数据库表或设计、大型依赖、未经批准模块及生成物。
- **架构证据**：未改变 V2.3 架构；若存在架构敏感文档变更，已按 ADR 流程批准。
- **审查证据**：按 [代码评审规则](../../governance/CODE_REVIEW_RULES.md) 完成评审，阻塞意见已解决。
- **完成定义证据**：按 [完成定义](../../governance/DEFINITION_OF_DONE.md) 对代码、测试、文档、审查和验收逐项给出结论；不适用项有批准依据。
- **验收证据**：每条 Phase 0 验收标准都有状态、证据引用、责任人和日期。

以上证据不要求使用特定命令或自动化工具，但必须真实反映所验证修订。

### 5.4 阻塞条件

出现以下任一情况即阻塞 Phase 0 退出：

- 交付物或验收标准缺失，或证据无法关联到待验证修订。
- 出现业务代码、服务实现、数据库设计、大型依赖或未来模块预建。
- 文档与实际仓库结构不一致，或治理规则之间存在未解决冲突。
- 存在未经批准的 V2.3 架构变化或未完成的架构阻塞意见。
- 任一强制证据状态为 `FAIL`、`BLOCKED` 或 `NOT RUN`。
- `N/A` 缺少客观理由或评审批准。
- 敏感信息、生产数据、凭据或不可接受的合规风险进入交付物或证据。
- 最终验收责任人尚未指定。

### 5.5 退出决定

- 所有进入条件满足、必需证据为 `PASS`、合法 `N/A` 已批准、阻塞条件全部清除且完成定义通过时，决定为 **允许退出 Phase 0**。
- 任一必需验证已执行但结果不符合预期时，决定为 **不允许退出**，修正后重新验证受影响范围。
- 因前置条件、权限、环境或外部依赖无法完成验证时，决定为 **暂停待决**，不得按通过处理。
- 允许退出 Phase 0 不自动批准 Phase 1 范围或工作。

## 6. Phase 1 最低验证 Gate

### 6.1 范围

Phase 1 Gate 只验证 Phase 1 章程、任务或 ADR **明确授权**的工程交付物及其质量证据。本文不定义 Phase 1 必须包含何种产品、模块、业务功能、服务、数据或技术。

如 Phase 1 实际范围尚未批准，本 Gate 只能作为治理模板，不能据此启动实现。

### 6.2 进入条件

除第 4 节通用条件外，必须确认：

- Phase 0 已有正式退出决定，或存在经批准且有期限的阶段例外。
- Phase 1 范围、责任边界和验收标准已由有权责任人批准。
- 所有新增或变化的架构、接口、数据、安全和依赖约束都有权威依据。
- 验证层级和方法依据风险选择，并明确哪些为人工证据、哪些为实际存在的自动化证据。
- 变更、兼容、回滚和残余风险的验证责任已指定。

### 6.3 必需证据

- **授权与范围证据**：每项交付物追溯到获批工作项，未实现未授权内容。
- **架构合规证据**：与 V2.3 架构、分层、职责及依赖规则一致；敏感变化关联 Accepted ADR。
- **完成定义证据**：代码、测试、文档、审查和验收五类门禁均有结论和引用。
- **验证覆盖证据**：适用的正常、边界、失败、兼容与恢复条件已验证；层级不适用时有批准说明。
- **分层测试证据**：在 Phase 1 范围获批后，Unit 与 Contract 按适用风险提供证据；涉及真实组件协作时补充 Integration。任何不适用层级都必须按证据标准批准，本文不因此授权实现。
- **接口与数据契约证据**：如获批范围涉及边界交换，契约语义、错误、版本、兼容和一致性规则已经验证。
- **安全与依赖证据**：敏感信息、权限边界、第三方依赖、许可证和已知风险按实际影响完成审查。
- **变更影响证据**：受影响资产、既有验证、文档、使用方和回滚条件已识别并验证。
- **缺陷与风险证据**：未解决事项具有等级、责任人、处置结论和接受权限；阻塞问题为零。
- **独立评审与验收证据**：强制检查、人工审查和指定验收均已完成。

若某一证据类别因实际获批范围客观不适用，必须使用 `N/A` 并满足 `test-evidence-standard.md` 的批准规则。

### 6.4 阻塞条件

- Phase 1 范围或验收标准未获正式批准。
- Phase 0 前置决定缺失且没有有效例外。
- 存在未经批准的架构、接口、数据、安全、依赖或阶段范围变化。
- 必需验证缺失、不可复现、与目标修订不匹配或状态不是 `PASS`。
- 失败路径、兼容性、恢复或回滚存在未解决的高影响缺口。
- 阻塞缺陷、安全问题、合规问题或未获授权接受的高风险仍开放。
- 文档、实现、契约和实际证据相互矛盾。
- 把尚不存在的 CI、框架、环境或自动化报告当作通过依据。

### 6.5 退出决定

- 所有强制项满足且残余风险由有权责任人接受时，决定为 **允许退出 Phase 1**。
- 存在实际失败或不符合验收标准的结果时，决定为 **不允许退出**。
- 因缺少前置条件、授权、可用验证上下文或外部决策而无法判断时，决定为 **暂停待决**。
- Phase 1 退出决定只证明获批范围达到最低门槛，不自动授权 Phase 2 内容。

## 7. Phase 2 最低验证 Gate

### 7.1 范围

Phase 2 Gate 只验证 Phase 2 正式范围内的交付物、跨交付物影响及面向下一阶段的工程就绪证据。本文不预设 Phase 2 的业务目标、系统形态、部署环境、用户、产品或技术栈。

“工程就绪”表示证据达到当前获批范围的最低治理标准，不表示生产、商业或发布就绪，除非相应目标已被另行明确授权并定义验收标准。

### 7.2 进入条件

除第 4 节通用条件外，必须确认：

- Phase 1 已有正式退出决定，或存在经批准且有期限的阶段例外。
- Phase 2 的目标、交付边界、接口责任、验收主体和风险接受权限明确。
- 变更影响分析覆盖相关层级、契约、数据、依赖、安全、可观测性、测试和文档；不适用项有依据。
- 验证计划包含回归范围、失败与恢复验证、兼容性和残余风险评审。
- 证据聚合规则已定义，能够从阶段结论追溯到单项证据和目标修订。

### 7.3 必需证据

- **端到端追溯证据**：阶段目标、工作项、验收标准、变更资产、验证记录、缺陷和退出结论形成闭环；“端到端”仅指治理追溯，不暗示某种测试产品。
- **适用分层证据**：在 Phase 2 范围获批后，Unit、Contract、Integration 与 E2E 按实际风险形成完整证据；若获批范围包含 Release，还必须具备 Release 验证准备和 Production Validation 计划。客观不适用项必须获批。
- **回归影响证据**：所有受影响的既有保证已重新验证，或有经批准的范围排除依据。
- **边界与兼容证据**：适用的跨层契约、版本、错误、数据一致性和迁移语义在实际获批范围内得到验证。
- **失败与恢复证据**：适用的失败条件、降级限制、恢复、回滚和未知结果处置均有可复核结论。
- **安全与治理证据**：权限、敏感信息、依赖、审计、保留、风险和例外满足现行规则。
- **运行责任证据**：若获批范围产生持续维护责任，所有者、观察方式、响应和退出条件已定义并验证；本文不假设运行环境存在。
- **证据质量审查**：证据完整、可追溯、可复现、最小披露且保留责任明确。
- **完成定义与验收证据**：`governance/DEFINITION_OF_DONE.md` 全部适用项通过，最终验收人明确签署结论。
- **残余风险决定**：所有未关闭风险均有影响、概率、措施、责任人和有权接受记录。

### 7.4 阻塞条件

- Phase 2 范围、前置阶段结论或退出权限不明确。
- 验收标准无法追溯到证据，或证据与目标版本、范围不一致。
- 适用的回归、边界、失败、恢复、安全或审计验证缺失。
- 任何强制证据为 `FAIL`、`BLOCKED` 或 `NOT RUN`，或 `N/A` 未获批准。
- 存在未解决的阻塞缺陷、架构冲突、安全/合规问题或未经授权接受的风险。
- 跨边界责任、残余风险、恢复或持续维护所有权存在空缺。
- 通过技术、环境或产品能力声明掩盖没有实际执行的验证。

### 7.5 退出决定

- 所有必需证据通过、完成定义满足、阻塞条件清除且残余风险获授权处理时，决定为 **允许退出 Phase 2**。
- 存在不符合验收标准或已确认失败时，决定为 **不允许退出**。
- 证据无法完成、责任未指定或外部决策缺失时，决定为 **暂停待决**。
- 退出 Phase 2 只证明明确范围内的 Gate 通过，不代表自动获得后续阶段、生产发布或商业化授权。

## 8. 状态汇总与退出规则

单项证据状态遵循 [测试证据标准](test-evidence-standard.md)：

| 证据状态 | Gate 处理 |
| --- | --- |
| `PASS` | 可计入已满足证据，但仍需审查完整性和适用范围 |
| `FAIL` | 阻止退出；修正后产生新的执行证据，历史失败记录保留 |
| `BLOCKED` | 暂停待决；必须记录阻塞原因、责任人和解除条件 |
| `NOT RUN` | 视为必需证据缺失，阻止退出 |
| `N/A` | 只有客观不适用且获评审批准时可排除；不得用于阶段 Gate 整体结论 |

Gate 总体退出决定只有三种：

- **允许退出**：全部强制条件满足。
- **不允许退出**：存在已确认的不符合或失败。
- **暂停待决**：因阻塞或证据不足暂时无法作出通过判断。

不得以多数证据通过抵消任一强制证据失败。

## 9. Gate 记录模板

```text
Gate 标识：<唯一标识>
阶段：<Phase 0 / Phase 1 / Phase 2>
批准范围：<任务、章程或决策引用>
目标修订：<不可歧义的修订标识>
进入条件结论：<满足 / 不满足>
必需证据清单：<Evidence ID 与状态>
批准的 N/A：<Evidence ID、理由、批准人；无则写“无”>
阻塞项：<问题、责任人、解除条件；无则写“无”>
残余风险：<风险编号与接受记录；无则写“无”>
完成定义结论：<通过 / 不通过>
退出决定：<允许退出 / 不允许退出 / 暂停待决>
决定人：<责任人>
决定日期：<无歧义日期>
复核或重开条件：<条件>
```

模板只定义逻辑记录，不指定文件格式、工具或存储位置。

## 10. 与完成定义的关系

- Gate 消费并汇总完成定义产生的代码、测试、文档、审查和验收证据，不能替代这些门禁。
- 单个工作项达到完成定义，不代表整个阶段 Gate 自动通过。
- 阶段 Gate 通过也不能把未达到完成定义的工作项追认为完成。
- `N/A` 必须同时满足 [完成定义](../../governance/DEFINITION_OF_DONE.md) 与本文的客观理由和评审批准要求。
- 实质性变更发生后，受影响证据和 Gate 决定必须重新评估。

## 11. 明确不在范围内

本文不定义真实测试、测试命令、测试数据、业务场景、产品行为、CI 配置、框架、环境拓扑或执行代码，也不新增或改变 V2.3 架构模块。任何后续具体验证设计必须基于已批准阶段范围另行制定。
