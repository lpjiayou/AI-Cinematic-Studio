# 测试层级定义

## 1. 目的

本文档以技术和框架无关的方式精确定义 Unit、Contract、Integration、E2E 与 Production Validation 的目标、范围、边界、进入证据、退出证据和不替代关系。层级选择必须基于风险与契约，不得从实现工具或目录结构反推。

这些定义只验证已批准的 V2.3 职责和边界，不新增模块、接口、业务流程或技术方案，也不改变 V2.3。

## 2. 层级关系总则

测试层级描述证据范围，不代表固定执行顺序、组织结构或技术栈。较高层级增加真实协作范围，但通常也引入更多状态与诊断复杂度；较低层级提供精确反馈，但不能证明未纳入范围的边界协作。

每项风险应由最低适当层级承担主验证，并按剩余风险补充其他层级。任何一层的通过都不能自动推导其他层已经通过。

## 3. Unit

### 目标

验证一个最小可隔离单元在受控输入和状态下的确定性行为，使局部规则错误能够被快速、准确地定位。

### 范围

- 一个明确测试单元及其公开可观察行为；
- 由该单元自身承担的输入判定、状态变化和错误语义；
- 通过已声明边界控制的协作者替代物。

### 边界

- 不访问真实网络、外部服务、持久化资源或不可控环境状态；
- 不验证两个真实技术组件之间的协作；
- 不复制其他层或组件的内部实现作为断言依据；
- 不把实现细节锁定为公开契约。

### 进入证据

- 被测责任与预期行为已经明确；
- 测试边界、受控输入和状态前提可被说明；
- 范围外依赖能够被隔离，且其替代只表达已声明契约。

### 退出证据

- 预期行为、边界条件和适用错误语义具有可重复结果；
- 结果能够明确归因于被测单元；
- 未覆盖风险、例外或不稳定结果已经登记并处置。

### 不替代关系

Unit 不替代 Contract 对跨边界兼容性的验证，不替代 Integration 对真实组件协作的验证，不替代 E2E 对系统级路径的验证，也不证明发布后部署状态。

## 4. Contract

### 目标

验证公开契约的提供方与消费方对可观察语义具有一致理解，并在允许的变化范围内保持兼容。
契约语义以 [接口契约基础](../04-interface-contract/README.md) 及后续获批的具体契约为依据，测试不能成为新的契约来源。

### 范围

- 已声明的输入、输出、错误、所有权和关联上下文语义；
- 消费方依赖的稳定承诺及提供方必须满足的边界；
- 契约变更对已知消费者的兼容性影响。

### 边界

- 只依赖公开契约，不读取或断言提供方内部实现；
- 不证明真实组件已经正确连接或部署；
- 不扩展未批准的接口、业务字段、协议或层间调用方向；
- 不以共享内部结构代替正式契约。

### 进入证据

- 契约范围、提供方、消费方和版本状态已经声明；
- 可观察成功与失败语义及适用关联上下文明确；
- 受影响消费者和兼容性风险已经识别。

### 退出证据

- 提供方与消费方针对同一契约语义获得一致、可重复的结果；
- 兼容与不兼容变化具有明确证据；
- 未解决分歧、例外及迁移要求已经登记。

### 不替代关系

Contract 不替代 Unit 对局部逻辑的精确验证，不替代 Integration 对真实连接与协作的验证，也不替代 E2E 对完整系统路径的验证。

## 5. Integration

### 目标

验证两个或以上真实技术组件在受控边界内能够按照已批准契约正确协作，并使配置、适配和交互问题可被发现。

### 范围

- 明确列出的真实组件及其连接边界；
- 公开契约在真实协作条件下的成功与失败行为；
- 与该协作直接相关的受控配置、状态和恢复条件。

### 边界

- 外部依赖必须可隔离、可重建且具有明确责任；
- 不扩展为完整系统或用户级路径；
- 不访问未授权生产资源、真实机密或不可恢复状态；
- 不通过断言私有内部结构来证明协作成功。

### 进入证据

- 参与组件、公开契约与交互范围已经明确；
- 相关 Unit 和 Contract 风险已有证据或获批例外；
- 环境、数据条件、隔离方式和清理责任可重复建立。

### 退出证据

- 真实组件的关键协作与适用失败行为得到可重复验证；
- 环境和测试状态已按约定清理或恢复；
- 发现的配置、契约或恢复缺陷已登记并完成处置判断。

### 不替代关系

Integration 不替代 Contract 的独立兼容性证明，不替代 Unit 的局部诊断能力，也不替代 E2E 对完整系统入口和跨边界路径的验证。

## 6. E2E

### 目标

通过正式系统入口，在受控的非生产验证环境中确认已批准系统级关键路径能够跨越相关边界并产生预期可观察结果。

### 范围

- 少量、风险优先的系统级关键路径；
- 路径涉及的正式入口、公开边界和最终可观察结果；
- 与路径直接相关的受控失败、恢复和清理行为。

### 边界

- 使用受控环境和测试数据，不持有生产机密或依赖真实生产状态；
- 不穷举所有局部规则、输入排列或组件内部行为；
- 不绕过正式入口直接修改内部状态来制造通过条件；
- 不以 E2E 数量代替低层风险与契约证据。

### 进入证据

- 候选版本、环境边界和正式入口已经确定；
- 相关 Unit、Contract 与 Integration 风险已有证据或获批例外；
- 测试数据、执行授权、停止条件和清理方案已经准备；
- 预期结果与失败判定可从已批准职责和契约追溯。

### 退出证据

- 选定路径的端到端结果、关联证据和失败判定可重复获得；
- 测试产生的状态已经清理或按约定隔离；
- 阻断缺陷、剩余风险和例外具有明确发布处置结论。

### 不替代关系

E2E 不替代 Unit、Contract 或 Integration 的精确证据，也不替代 Production Validation 对实际部署结果的发布后确认。E2E 必须在受控非生产验证环境完成，不能推迟到生产环境补做。

## 7. Production Validation

### 目标

在发布完成后，以预先批准、可停止和低风险的方式确认已部署版本、生产环境及必要技术信号符合本次发布预期。

Production Validation 是发布后受控验证，不是生产业务测试。它不探索产品行为、不验证新的业务需求，也不以真实用户活动代替测试证据。

### 范围

- 本次已批准发布及其部署身份；
- 发布计划中预先声明的最小技术验证项；
- 与发布直接相关的技术健康、可观察结果和回滚判定；
- 验证活动自身的开始、停止、升级和清理证据。

### 边界

- 不补做 Unit、Contract、Integration 或 E2E；
- 不执行未批准业务流程、探索性业务测试、容量实验或破坏性操作；
- 不创建无授权真实业务状态，不使用未获授权生产数据；
- 不绕过正式生产入口、访问控制、审计或发布治理；
- 验证失败必须按预定条件停止、回滚或升级，不得反复尝试直至偶然成功。

### 进入证据

- 发布已经获批并完成部署，候选身份可追溯；
- 所有发布前测试层级已有所需退出证据或正式例外；
- 验证计划、执行责任人、授权范围和时间边界已经批准；
- 安全约束、停止条件、回滚或升级路径已经准备；
- 预期技术信号与成功、失败判定已经声明。

### 退出证据

- 每个批准验证项均有时间、执行责任与可追溯结果；
- 成功时确认已部署版本满足预先声明的技术发布预期；
- 失败时已经按计划停止、回滚或升级，并形成缺陷或事件记录；
- 验证产生的临时状态已经清理，剩余风险已有明确 owner。

### 不替代关系

Production Validation 不替代任何发布前测试层级、发布审批、监控或事件响应。它不能作为缺失 E2E 或其他证据的补偿手段，也不能被解释为允许在生产环境测试业务。

## 8. 未来资产位置

以下路径仅作为未来获批测试资产的保留位置，不表示测试代码、框架或自动化已经存在：

| 测试层级 | 未来位置 | 当前含义 |
| --- | --- | --- |
| Unit | `tests/unit/` | 仅保留分类位置 |
| Contract | `tests/contract/` | 仅保留分类位置 |
| Integration | `tests/integration/` | 仅保留分类位置 |
| E2E | `tests/e2e/` | 仅保留分类位置 |

Production Validation 属于发布后的受控验证活动，不新增 `tests/` 子目录。其计划与证据的正式归档位置应由后续获批的发布和可观测性治理规定，本任务不预先创建路径。
具体流程见 [Release 验证流程](release-validation.md)。

## 9. 变更控制

新增测试层级、改变任一层级责任或调整 Production Validation 边界，必须关联独立任务并评估对架构、契约、发布和缺陷治理的影响。任何测试层级定义都不得用于新增或改变 V2.3 模块职责。
