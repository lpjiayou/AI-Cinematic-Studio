# 测试策略

## 1. 目的与范围

本文档定义 AI Cinematic Studio 的测试治理原则，用于指导后续获批实现如何选择验证层级、建立可信证据并管理缺陷与例外。它不选择语言、测试框架、执行工具、平台或供应商，也不包含测试代码、业务场景或具体测试用例。

本策略适用于 Unit、Contract、Integration、E2E 与 Production Validation 五类验证活动。各层级的精确定义见 [测试层级](test-levels.md)，验证记录遵守 [测试证据标准](test-evidence-standard.md)。测试策略只验证已批准的职责和契约，不新增、推导或改变 V2.3 模块架构。

## 2. 核心原则

### 2.1 风险驱动

测试投入必须由风险决定，而不是由目录、实现规模或固定数量指标决定。每项变更在选择验证方式前，应识别：

- 可能受影响的职责、公开契约和依赖边界；
- 失败影响、发生可能性与被其他控制发现的难度；
- 变更可逆性、影响传播范围和恢复复杂度；
- 安全、隐私、合规、可靠性与数据完整性风险；
- 现有证据是否足以覆盖新增或变化的风险。

高风险不等于只增加高层测试。应优先在能够最准确、最确定地发现问题的最低适当层级建立证据，再按剩余跨边界风险补充其他层级。

### 2.2 分层验证

每个测试层级只承担自身能够可靠验证的责任：

- Unit 验证隔离单元的确定性行为；
- Contract 验证公开边界的语义与兼容性；
- Integration 验证真实组件之间的受控协作；
- E2E 验证受控环境中的系统级关键路径；
- Production Validation 在发布后验证已部署版本的受控技术状态。

层级之间互为补充，不允许以少量高层测试替代低层精确证据，也不允许以大量低层测试证明真实边界协作或部署结果。

### 2.3 契约优先

跨层或跨组件行为必须先有可评审的公开契约，再建立相应验证。契约验证关注可观察的输入、输出、错误、兼容性、所有权和关联上下文，不依赖提供方内部实现。

未声明的隐式行为、共享状态或内部结构不能作为稳定测试依据。契约发生变化时，应先识别消费者影响并更新契约证据，再允许依赖方采用变化。
接口、事件、错误和统一标识的权威语义来自 [接口契约基础](../04-interface-contract/README.md)，Contract 验证不得自行扩展这些定义。

### 2.4 确定性

在相同受控前提、输入和状态下，验证应产生一致且可解释的结果。时间、随机性、并发、环境差异及外部状态等非确定因素必须被显式控制、隔离或记录。

偶发成功不能作为通过证据。结果不稳定的验证必须作为缺陷处理，在恢复可信度前不得被静默忽略、无限重试或包装为正常波动。

### 2.5 隔离

验证范围必须清晰，范围外依赖应被受控替代、隔离或纳入更高层级。测试不得无授权地访问真实生产数据、生产机密、不可恢复资源或无法控制的外部状态。

隔离不等于复制另一边界的内部实现。替代物只能表达已声明契约，不能通过模拟细节制造与真实边界不一致的通过结果。

### 2.6 可重复

测试证据必须能够由具备相同授权的独立执行者重新获得。每项验证应记录必要前提、受控数据条件、环境假设、执行范围、结果判定和清理要求。

仅在个人环境、未记录状态或一次性手工操作下得到的结果，不构成可重复的发布或合并证据。

### 2.7 证据优先

“已测试”必须由可追溯证据支持。证据至少应回答：

1. 验证了哪项已批准职责、契约或风险；
2. 在哪个测试层级、什么受控前提下验证；
3. 预期判定与实际结果是什么；
4. 哪些风险仍未覆盖，以及由谁接受；
5. 证据由何次变更产生，何时需要重新验证。

测试数量、覆盖率数值或执行成功状态本身不能代替风险与契约覆盖说明。本阶段不规定证据工具或存储格式。

## 3. 测试选择流程

每项获批变更应按以下顺序形成测试计划：

1. 确认变更范围及其 V2.3 责任边界；
2. 识别受影响的公开契约、依赖方向和质量风险；
3. 为每项风险选择最低适当测试层级；
4. 识别需要 Contract、Integration 或 E2E 补充的跨边界风险；
5. 判断发布后是否需要 Production Validation，并单独记录安全边界；
6. 明确进入条件、退出证据、责任人和未覆盖风险；
7. 在变更合并或发布前完成评审要求。

不得从“某个目录已经存在”推导某类测试已经完成，也不得为了满足层级数量而创建没有风险依据的验证。

## 4. 缺陷治理

任何验证发现的预期与实际差异都必须可追踪，至少记录：

- 发现证据、影响范围和对应风险；
- 当前责任边界与处置 owner；
- 是否阻断合并、发布或继续验证的判断依据；
- 修复、缓解、回滚或接受风险的决定；
- 防止重复发生所需的回归证据；
- 关闭条件及独立复核结果。

修复测试本身不能自动关闭产品或架构缺陷；必须确认原始风险已经被有效控制。重复、逃逸或不稳定缺陷应触发对测试层级选择、契约清晰度和隔离策略的复审。

不得删除失败证据、降低判定标准或禁用验证来制造通过结果。确需暂时停用时，必须进入例外治理。

## 5. 例外治理

无法在规定时点满足测试要求时，例外申请必须在合并或发布前获批，并至少包含：

1. 关联变更、缺失证据与具体原因；
2. 受影响风险、契约和层级；
3. 责任人、批准人和适用范围；
4. 临时补偿控制与监测方式；
5. 明确到期日期或到期事件；
6. 恢复测试、消除例外和复核结果的计划。

例外不等于测试通过，也不得被后续变更自动继承。高风险未覆盖、未知影响、无责任人或无退出计划的申请不能作为有效例外。永久改变测试要求必须更新治理基线，不得通过连续延期维持。

## 6. Production Validation 治理边界

Production Validation 是发布完成后的受控技术验证，用于确认已部署版本、运行环境和必要技术信号符合已批准发布预期。它不是生产环境中的业务测试，不得用于探索业务行为、补做发布前 E2E、产生无授权业务活动或绕过发布门禁。

所有 Production Validation 必须预先规定安全范围、责任人、停止条件、回滚或升级路径及证据要求。任何可能改变真实业务状态、影响真实用户或使用未获授权生产数据的行为，都不因被称为“验证”而获得许可。

## 7. 阶段边界与变更控制

当前阶段只建立策略和未来测试资产位置，不编写测试代码、业务场景、工具配置或自动化流程。测试策略变化必须关联独立任务，并评估对契约、发布、缺陷治理和 V2.3 架构基线的影响；本文件不得作为修改 V2.3 的途径。
测试可以依赖获批的被测公开资产，但生产代码不得依赖 `tests/`、测试夹具或测试专属配置；详细依赖边界见 [依赖规则](../../architecture/dependency-rules.md)。
