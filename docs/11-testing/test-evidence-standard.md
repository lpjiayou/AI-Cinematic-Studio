# AI Cinematic Studio 测试证据标准

## 1. 文档定位

本文定义 ACS 验证与测试证据的最低元数据、状态语义、完整性、可追溯性、复现性、最小披露、保留和审查规则，并提供框架无关的记录模板。

本文不包含真实测试、真实命令、代码、测试数据、业务场景、产品名称或工具配置，不假定 CI、测试框架、共享环境或自动化能力已经存在。本文不改变 V2.3 架构，所有具体验证必须基于获批任务范围。

## 2. 证据的定义

测试证据是能够让独立评审者判断“在什么对象、修订和上下文中，以何种方法验证了什么预期，并实际得到什么结果”的可复核记录。

证据可以由人工验证或实际存在且获准使用的自动化能力产生。来源不同不改变证据标准；工具输出本身也不自动构成完整证据，必须补齐本标准要求的上下文和责任信息。

## 3. 证据原则

- **真实性**：只记录实际执行和观察到的结果，不把计划、预测或历史结果当作本次结果。
- **完整性**：证据包含判断结论所需的全部上下文、预期、实际结果和限制。
- **可追溯**：证据可追溯到工作项、验收标准、目标修订、执行责任和审查结论。
- **可复现**：合格人员可以根据记录在等价受控上下文中重复验证，或明确理解为何无法重复。
- **最小披露**：只保留证明结论所需的信息，不暴露凭据、个人信息、生产数据或内部敏感细节。
- **历史保真**：失败、受阻和未运行状态不得因后续成功而被删除或改写。
- **框架无关**：逻辑要求不依赖特定测试库、CI 产品、操作系统、云平台或命令行工具。

## 4. 必需证据元数据

每一条独立证据记录必须包含以下元数据：

| 元数据 | 必填内容 |
| --- | --- |
| **Evidence ID** | 唯一、不可复用且不承载敏感或业务信息的证据标识 |
| **标题与验证目标** | 简洁说明要证明或否定的质量命题 |
| **关联范围** | 获批阶段、任务、变更或缺陷引用，以及明确不在范围内事项 |
| **验收标准引用** | 该证据支持的一个或多个可验证标准；没有关联时必须说明治理依据 |
| **目标对象与修订** | 被验证资产及不可歧义的版本、修订或文档状态 |
| **验证层级或类型** | `Unit` / `Contract` / `Integration` / `E2E` / `Production Validation`，或结构检查、文档审查等已批准类型；仅记录实际适用项 |
| **验证方法** | 足以复现的逻辑步骤、检查点和判定方式；不要求使用特定框架或命令 |
| **前置条件与输入** | 所需状态、受控输入、假设及其来源；敏感内容使用安全引用而非复制 |
| **验证上下文** | 实际使用的环境特征、配置类别和依赖版本；不存在共享环境时如实描述本次上下文 |
| **预期结果** | 执行前定义的、可客观判断的完成条件 |
| **实际结果** | 实际观察、差异、限制和必要的非敏感产物引用 |
| **状态** | `PASS` / `FAIL` / `BLOCKED` / `NOT RUN` / `N/A` 之一 |
| **执行责任与时间** | 执行人或责任团队，以及无歧义的执行时间 |
| **关联缺陷、风险或例外** | 发现的问题、阻塞、批准例外和风险编号；无则明确写“无” |
| **证据产物引用** | 输出、截图、报告或审查记录的稳定引用；无产物时说明如何复核 |
| **限制与适用边界** | 证据不能证明的事项、已知不确定性和外推限制 |
| **审查记录** | 评审人、审查日期、审查结论和意见处理情况 |
| **保留责任** | 保留分类、责任人、复核/处置条件和访问限制 |

物理字段名、记录格式和存储位置由后续获批治理方案决定，本文不创建 Schema 或数据库设计。

## 5. 状态定义

每条证据在任一时点只能有一个当前状态；状态更新必须保留历史。

### `PASS`

仅在以下条件全部满足时使用：

- 验证已在所记录的目标修订和上下文中实际执行。
- 实际结果满足预先定义的预期结果和全部适用验收标准。
- 没有未记录的差异、阻塞或会改变结论的限制。
- 必需元数据、产物引用和审查信息完整。

部分通过、预期将通过、历史曾通过或工具退出正常都不足以单独判定 `PASS`。

### `FAIL`

当验证已经实际执行，但任何适用预期结果或验收标准未满足时使用。

- 必须记录预期与实际差异、影响和关联缺陷或风险。
- 后续修复并通过时，应形成新的执行记录或新修订，而不是覆盖原失败证据。
- `FAIL` 表示已获得不符合证据，不等同于“未执行”。

### `BLOCKED`

当计划验证因明确的前置条件、权限、依赖、环境、数据或外部决策缺失而无法完成时使用。

- 必须记录已完成到哪一步、阻塞原因、责任人、解除条件和目标复核时间。
- `BLOCKED` 不能因阻塞不属于执行人控制而视为通过。
- 阻塞解除后必须实际重新执行并产生新的状态结论。

### `NOT RUN`

当验证尚未执行，且不存在已确认阻塞或客观不适用理由时使用。

- 必须说明未运行原因、计划责任人和后续决定。
- 计划中的检查、空白报告或只有测试定义没有执行记录均为 `NOT RUN`。
- 强制证据为 `NOT RUN` 时不能满足完成定义或阶段 Gate。

### `N/A`

仅当验证项目对当前获批范围客观不适用时使用。

- 必须说明适用性判断、事实依据、影响和批准人。
- 不得因环境缺失、执行成本、时间不足、测试困难或失败风险使用 `N/A`；这些情况应为 `BLOCKED`、`NOT RUN` 或 `FAIL`。
- `N/A` 必须经证据评审人确认，并符合 [完成定义](../../governance/DEFINITION_OF_DONE.md) 的不适用项规则。
- 阶段 Gate 整体不能标记为 `N/A`。

## 6. 状态聚合规则

- 强制证据只有 `PASS` 或经批准的 `N/A` 才可计入已满足。
- 任一强制证据为 `FAIL`，对应验收标准和 Gate 不得通过。
- 任一强制证据为 `BLOCKED` 或 `NOT RUN`，对应结论保持未完成。
- 多个 `PASS` 不能抵消一个强制 `FAIL`。
- 汇总状态必须能下钻到每条原始证据，不能只保留百分比或单一总分。
- 同一验证在不同修订、上下文或时间重新执行时，应形成可区分记录并保留相互关系。
- 证据状态与缺陷状态相互关联但不等同；关闭缺陷不能自动把既有 `FAIL` 改为 `PASS`。

## 7. 完整性规则

- 证据必须覆盖其声称证明的全部预期结果，不能只选择有利片段。
- 原始观察、摘要、截图或输出之间不得存在未解释矛盾。
- 人工编辑、脱敏、格式转换或截取必须说明范围，且不得改变判断语义。
- 证据必须绑定目标修订；修订发生实质性变化后，旧证据不能直接证明新修订。
- 证据产物缺失时必须说明替代复核方式；仅有结论文字且无法复核不满足完整性。
- 生成时间、执行时间和审查时间应可区分；不得使用后补时间掩盖实际执行顺序。
- 任何已知限制都必须显式记录，不能在汇总时被省略。

## 8. 可追溯规则

证据链至少应支持双向追溯：

- 从阶段目标、任务和验收标准定位到所有适用 Evidence ID。
- 从 Evidence ID 定位到目标修订、验证方法、实际结果、执行责任和审查决定。
- 从 `FAIL`、`BLOCKED` 或例外定位到缺陷、风险、责任人和后续处置。
- 从架构敏感验证定位到对应权威文档和 Accepted ADR。
- 从阶段 Gate 决定定位到所汇总的全部强制证据及批准的 `N/A`。

禁止使用易变展示名称、个人本地路径或无法访问的临时位置作为唯一追溯依据。

## 9. 复现规则

一条可复现证据必须说明：

1. 目标对象和修订。
2. 前置条件、受控输入及假设。
3. 验证上下文中会影响结果的特征和依赖。
4. 逻辑执行步骤、观察点和预期判定。
5. 实际结果的获取和复核方式。
6. 已知非确定因素、容差和失败处理。

- 不要求记录真实命令；若未来具体证据使用命令或工具，应以受控引用保存，不能在本标准中预设。
- 复现不要求使用相同品牌或产品，但等价上下文必须满足影响语义的条件。
- 无法完全复现的验证必须说明原因、可重复部分、替代证据和残余风险，不能直接宣称完整通过。
- 依赖外部状态的证据应记录当时可验证快照或权威引用，不假设未来仍保持相同状态。

## 10. 最小披露与安全规则

- 证据不得包含凭据、令牌、密钥、未授权个人信息、生产数据、客户内容、内部堆栈或基础设施秘密。
- 只保留支持结论所需的最少输入与输出；可使用脱敏样本、受控引用或摘要时，不复制原始敏感内容。
- 脱敏必须保持测试意义，并记录脱敏责任和对结论的限制。
- 标识符、路径、截图、日志和自由文本都必须接受敏感信息检查，不能因其是“测试输出”而豁免。
- 必须按最小权限限制证据访问；评审可见不等于所有仓库使用者均可见。
- 发现证据泄露敏感信息时，应立即停止常规分发、登记风险并按安全治理流程处置，不能只删除引用掩盖事件。

## 11. 保留与处置规则

- 保留期限和方式应基于阶段、变更风险、审计义务、缺陷生命周期和适用政策确定；本文不规定具体时长或存储产品。
- `FAIL`、`BLOCKED` 和 `NOT RUN` 证据与 `PASS` 证据同样属于审计历史，不能因结论不利而提前删除。
- 至少在相关 Gate、风险、缺陷、例外和变更仍有效期间保持证据可访问和可追溯。
- 证据归档必须保持 Evidence ID、状态历史、元数据、访问限制和复核能力。
- 证据处置需要明确授权、范围、保留义务复核和完成证明；含有安全事件信息的证据还须遵守对应保全要求。
- 引用目标被迁移或归档时，应维护稳定追溯关系，不能让历史 Gate 失去依据。

## 12. 审查规则

证据评审人必须检查：

- 元数据是否完整，状态是否符合第 5 节定义。
- 目标修订、范围、预期、实际结果和产物是否一致。
- 验证方法是否适合所声明的质量命题，是否存在遗漏或无依据外推。
- `N/A`、限制、例外和残余风险是否有客观依据与正确批准权限。
- 证据是否可追溯、可复现且满足最小披露与保留要求。
- 证据能否支持 [完成定义](../../governance/DEFINITION_OF_DONE.md) 及适用阶段 Gate 的结论。

高风险或架构敏感证据应由独立评审人审查。作者自检不能替代所需独立审查；确实无法分离时，必须获得项目负责人批准并记录补偿控制。

评审后证据发生实质性变化时必须重新审查。审查意见、处理结果和最终批准均需保留。

## 15. 与完成定义和阶段 Gate 的一致性

- 本标准为 [完成定义](../../governance/DEFINITION_OF_DONE.md) 中代码、测试、文档、审查和验收结论提供统一证据语义，但不能替代任何一类门禁。
- 工作项只有在全部适用证据通过、合法 `N/A` 已批准且阻塞问题清除后，才能支持“完成”结论。
- 阶段 Gate 按 [验证 Gate](verification-gates.md) 汇总证据；单项 `PASS` 不能直接推导阶段退出。
- 实质性变更使既有证据失去适用性时，必须重新执行受影响验证并保留新旧记录关系。
- 证据标准不能被用于授权未批准范围、业务实现、技术选型或 V2.3 架构变更。

## 16. 明确不在范围内

本文不提供真实测试用例、命令、脚本、代码、测试数据、产品名称、CI 配置、框架选择、环境搭建或 V2.3 架构修改。Phase 0 只建立测试证据治理标准。
