# AI Cinematic Studio 事件契约标准

## 1. 文档定位

本文定义 ACS 事件在架构边界之间交换时必须遵循的**逻辑语义契约**。它只约束信息含义、责任与演进规则，不规定任何序列化格式、编程语言、消息系统、传输协议或运行时实现。

本文不创建具体事件，不实现代码，不引入技术选型，不设计数据库，也不改变 V2.3 架构。未来具体事件只有在相应阶段获得授权并完成契约评审后，才能基于本标准定义。

## 2. 规范用语

- **必须**：强制要求；不满足即不符合本契约。
- **不得**：明确禁止的行为。
- **应**：除非存在经记录和批准的理由，否则应遵守。
- **可**：由具体事件契约在不破坏本标准的前提下选择。

## 3. 核心原则

- **语义先于载体**：事件含义不能依赖某种编码、队列或框架才能理解。
- **事实不可变**：一个已形成的事件表示某个时点已经发生的事实；不得修改后继续沿用原 Event ID。
- **身份与内容分离**：标识符只承担关联作用，不承载业务含义或权限结论。
- **最小披露**：只携带理解该事实所必需的信息，不复制无关状态。
- **显式关联**：只在满足条件时携带上下文标识，不得为了字段齐全而伪造关联。
- **可追溯演进**：事件语义的变化必须可识别、可评审并能说明兼容性影响。
- **依赖方向不变**：事件数据可以按获批契约被观察或返回，但不得使下层依赖上层、绕过相邻层或建立循环依赖。

## 4. 必填逻辑字段

每一个符合本标准的事件都必须包含以下五个逻辑字段。字段的物理名称、编码与表现形式由未来获批的技术绑定契约决定；技术绑定不得改变本节语义。

| 必填字段 | 规范语义 | 约束 |
| --- | --- | --- |
| **Event ID** | 本次事件事实的唯一标识 | 必须唯一、不可变、不可复用且对使用方表现为不透明值；不得编码模块、环境、租户、时间或业务含义。重新形成的事件必须拥有新的 Event ID。 |
| **Event Type** | 事件事实的稳定语义类型 | 必须由获批的具体事件契约定义；同一类型不得在不声明兼容性变化的情况下改变含义。不得从 Source、Payload 结构或传输目的地推断 Event Type。本文不枚举任何具体事件类型。 |
| **Source** | 形成该事件事实的逻辑来源 | 必须指向经架构授权的逻辑来源边界，而不是主机名、进程号、部署位置或供应商产品。Source 不自动等同于契约责任人，也不构成真实性或权限证明。 |
| **Payload** | 理解该事件事实所需的事件专属信息 | 必须存在，并由具体事件契约定义其语义、必填内容与敏感性。仅当具体契约明确允许时才可表达为“无附加内容”。不得塞入完整内部模型、凭据、无关上下文或仅供调试的数据。 |
| **Timestamp** | 该事件所描述事实发生的时间点 | 必须表达无歧义的时间点，并与发送、接收、持久化或处理时间区分。精度和技术表现由后续绑定契约规定，不得用接收时间静默替代未知的发生时间。 |

### 4.1 字段完整性

- 生产方必须在事件越过责任边界前提供全部必填字段。
- 必填字段缺失、不可解析或违反约束时，接收方必须将其视为契约不合规，不得自行猜测或补造语义。
- Payload 中重复出现的封套字段不能覆盖顶层逻辑字段；发现冲突时，以契约不合规处理。
- Event ID 只标识事件事实，不表示处理成功、只处理一次或全局顺序。

## 5. 条件关联标识

以下标识不是所有事件的无条件必填字段。只有满足对应条件时才应关联；不满足时不得生成虚假值、默认值或无来源值。

| 条件关联 | 何时关联 | 关联规则 |
| --- | --- | --- |
| **Request ID** | 事件由一个可识别请求直接触发，或其因果链明确要求回溯该请求时 | 必须沿用该因果链中已确立的 Request ID。一个事件没有请求来源时不得为了追踪便利虚构 Request ID。Request ID 不代表调用者身份或授权结果。 |
| **Trace ID** | 事件属于一个已建立的端到端技术追踪上下文时 | 必须保持既有 Trace ID 的连续性。本文不要求为没有追踪上下文的事件创建 Trace ID，也不规定追踪系统或采样方式。 |
| **Project ID** | 事件所描述的事实明确归属于一个已识别项目，且具体事件契约将项目定义为有效上下文时 | 必须使用权威上下文中已有的 Project ID，不得根据名称或 Payload 内容推测。Project ID 仅用于关联，不能代替项目访问控制。 |
| **Asset ID** | 事件直接描述某个已识别资产，且该资产是具体事件契约定义的关联主体时 | 必须引用权威 Asset ID；不得将文件路径、外部地址或展示名称当作 Asset ID。没有直接资产关联时应省略。 |
| **Job ID** | 事件产生于或直接描述一个已识别作业的执行生命周期时 | 必须沿用该执行上下文的 Job ID。Job ID 不表示作业状态、成功与否或重试次数。非作业事件不得伪造关联。 |

### 5.1 关联组合规则

- 一个事件可同时满足多个关联条件，各标识保持独立语义。
- 关联标识之间不得相互推导；例如存在 Job ID 不自动意味着存在 Project ID 或 Asset ID。
- 标识之间的一致性和授权关系必须由其权威边界验证，不能仅凭事件携带某个 ID 建立信任。
- 具体事件需要表达多个同类关联对象时，必须在其 Payload 契约中明确基数和角色；不得通过重复或拼接顶层标识表达。
- 生产方负责传播已有且适用的关联；接收方不得在缺少权威依据时补造关联。

## 6. 生产方与接收方责任

### 生产方

- 对 Event Type、Source、Payload 和 Timestamp 的真实性与契约合规性负责。
- 生成不可复用的 Event ID，并仅传播满足条件的关联标识。
- 在越过边界前完成必填、类型、约束及敏感信息检查。
- 不得因接收方当前实现细节改变事件的稳定语义。

### 接收方

- 按获批契约解释事件，不从字段排列、传输位置或内部实现推断额外语义。
- 对缺失、冲突或不受支持的契约内容采用显式错误处理，不静默降级。
- 不把事件中的标识符当作身份认证、授权或数据所有权证明。
- 兼容性处理只能遵循已发布的演进规则。

### 契约责任人

- 维护具体 Event Type 的语义、Payload 定义、关联条件、敏感等级和演进记录。
- 确保契约经过架构、接口、安全和测试评审。
- 责任人尚未正式指定时，由项目负责人明确指定，不得由实现方自行假设。

## 7. 演进与兼容性

- Event Type 的既有含义一经发布不得重新解释或复用为另一事实。
- 删除必填信息、改变字段含义、放宽或收紧关键约束、改变关联条件，均属于需要显式兼容性评估的变更。
- 不兼容变化必须建立新的、可区分的契约身份，并提供迁移、并行验证和退出计划；本文不规定版本编码方式。
- 仅增加信息也必须评估接收方容忍能力、最小披露和安全影响，不能默认视为无风险。
- 废弃契约时必须保留决策记录、使用方影响、过渡期和关闭证据。
- 架构敏感变化必须遵守 [架构变更流程](../../governance/ARCHITECTURE_CHANGE_PROCESS.md)，不能通过事件契约反向修改 V2.3 架构。

## 8. 安全与数据最小化

- Payload 和关联标识只能包含完成契约目的所需的信息。
- 不得携带密钥、令牌、认证材料、未获授权的个人信息、内部堆栈或调试转储。
- Source 与任何关联 ID 都是不透明声明，不能单独建立信任；真实性、完整性与访问控制由未来获批的安全机制负责。
- 生产方必须按字段敏感性控制披露，接收方必须按最小权限使用和保留。
- 错误信息应遵循 [错误码标准](error-code-standard.md)，不得将敏感诊断内容塞入 Payload 规避错误安全规则。

## 9. 明确不在本文范围内

本文不选择或定义：

- JSON、XML、Protocol Buffers 或任何其他序列化方式。
- 消息代理、队列、事件总线、数据库或供应商产品。
- 发布/订阅、请求/响应或其他交互实现。
- 至少一次、至多一次、恰好一次等交付语义。
- 顺序、重试、确认、幂等、去重、保留或回放机制。
- 任何具体事件名称、业务事件、Payload 结构或路由规则。
- V2.3 架构之外的新模块、服务或部署关系。

这些事项如在后续阶段需要定义，必须由独立且获批的契约或 ADR 承担，不能从本文推断。

## 10. 契约检查清单

具体事件契约只有在以下问题均有明确答案后才可进入评审：

- 五个必填字段的语义和约束是否完整且与本文一致？
- 每个条件关联标识是否有清晰的携带与省略条件？
- Event Type 是否表示单一稳定事实，且未复用既有语义？
- Payload 是否最小、无敏感泄露且没有复制内部模型？
- 生产方、接收方和契约责任人是否明确？
- 兼容性、废弃、安全和验证要求是否可执行？
- 是否完全避免引入技术选型、业务实现、数据库设计或 V2.3 架构变更？

Phase 0 只建立本标准，不创建具体事件契约或实现。
