# AI Cinematic Studio 错误码与错误语义标准

## 1. 文档定位

本文定义 ACS 跨架构边界错误表达的稳定语义、逻辑字段、责任、安全规则与抽象分类。它是技术无关的接口治理标准，不规定编程语言异常、序列化格式、传输协议或运行时框架。

本文不实现代码，不枚举业务错误码，不映射 HTTP 或 gRPC 状态，不引入任何技术选型，不设计数据库，也不改变 V2.3 架构。具体错误码只能在未来阶段获得授权、明确责任边界并完成契约评审后登记。

## 2. 核心概念

### 2.1 错误语义

错误语义描述“什么契约条件未满足、由哪个责任边界报告、使用方可以采取什么受控行动”。稳定语义是机器判断和兼容性治理的依据，不能依赖人类可读文案、日志文本或传输状态。

### 2.2 Error Code

Error Code 是某一种稳定错误语义的符号标识。它必须：

- 在其获批责任范围内唯一且不可复用。
- 对同一语义保持稳定，不因文案、实现、部署或传输方式变化而改变。
- 不编码 HTTP/gRPC 状态、时间、环境、主机、版本、严重度、租户或实体标识。
- 不使用可能变化的内部类名、函数名、供应商名称或文件路径。
- 由明确责任人登记并附语义、分类、恢复建议和生命周期状态。

本文不规定 Error Code 的字符格式、命名空间表达或任何具体值。表现规则必须由后续获批的技术绑定契约定义，且不得改变错误语义。

### 2.3 Error Occurrence ID

Error Occurrence ID 标识一次具体错误实例，用于关联诊断。它与 Error Code 不同：同一 Error Code 可对应多次独立发生，每次发生都应有不同的 Error Occurrence ID。

Error Occurrence ID 不得携带业务信息，也不应被使用方用于判断错误类别或恢复策略。

## 3. 稳定错误语义规则

- 一个 Error Code 只对应一个明确语义；不得根据调用位置、Payload 或文案赋予不同含义。
- 既有 Error Code 的含义不得被重新解释、扩大或复用于新条件。
- 语义发生实质变化时必须登记新的 Error Code，并执行兼容性与迁移评审。
- 人类可读 Message 可以改写或本地化，但不能成为程序判断依据。
- Category 只提供高层分组，不能替代具体 Error Code。
- Retry Guidance 必须由具体错误语义定义，不能仅凭 Category 或传输状态推断。
- 一个边界在不确定具体原因时不得猜测更精确的错误；应使用该边界已登记的安全、稳定兜底语义，并保留受控内部诊断。
- 外部错误翻译必须保留原语义或显式说明信息收敛，不能伪造底层原因。
- 每个相邻边界只公开自己拥有的稳定错误语义；不得将更下层的内部错误、异常或诊断细节不加转换地穿透多个层级。
- 错误返回与边界转换不构成反向依赖，也不得授权接收方直接访问报告方或更下层的内部实现。

## 4. 逻辑字段

以下字段描述逻辑信息，不规定物理字段名或编码形式。

### 4.1 必填字段

| 字段 | 语义与约束 |
| --- | --- |
| **Error Code** | 稳定错误语义的唯一符号标识；必须已登记且处于允许使用的生命周期状态。 |
| **Category** | 本标准第 5 节定义的抽象类别；用于高层治理，不得承担具体业务分支语义。 |
| **Error Occurrence ID** | 本次错误实例的唯一、不透明且不可复用标识。 |
| **Message** | 面向预期接收者的安全摘要；不得包含敏感诊断，且不得作为机器分支条件。 |
| **Source** | 对错误表达负责的逻辑边界；不得使用主机、进程或内部代码位置代替。 |
| **Timestamp** | 错误被该 Source 确认发生的无歧义时间点；技术格式由后续绑定契约决定。 |
| **Retry Guidance** | 明确说明“不可重试”“仅满足已述条件后可重试”或“调用方不得自行判断”；必须描述适用条件，不能承诺未定义的重试机制。 |

### 4.2 条件字段

| 字段 | 使用条件 | 约束 |
| --- | --- | --- |
| **Safe Details** | 接收方确需额外信息才能理解或纠正请求时 | 只包含契约明确允许的非敏感内容；不得暴露堆栈、查询、路径、凭据或内部拓扑。 |
| **Cause Reference** | 当前错误由另一已标识错误直接引起且允许披露关联时 | 关联 Error Occurrence ID 或受控诊断引用，不复制敏感底层细节。 |
| **Request ID** | 错误与一个已建立请求直接关联时 | 沿用已有标识，不得补造；不表示身份或授权。 |
| **Trace ID** | 错误处于已建立的追踪上下文时 | 沿用已有标识；本文不规定追踪技术。 |
| **Project ID / Asset ID / Job ID** | 具体错误契约明确要求相应上下文，且关联来自权威来源时 | 仅用于关联，不构成访问权限、所有权或存在性证明；不得由文案或非权威内容推测。 |
| **Documentation Reference** | 存在面向接收方且版本受控的恢复说明时 | 指向稳定文档标识；不得用易变内部地址承载唯一语义。 |

### 4.3 字段处理规则

- 生产方必须提供全部必填字段；缺失时属于错误契约不合规。
- 条件字段只在满足条件且允许披露时提供，不使用空占位或虚假标识。
- 接收方不得从 Message、Source 名称或标识符结构推断未声明语义。
- 诊断信息若不适合跨边界披露，应保留在受控内部诊断渠道，而不是放入错误契约。

## 5. 抽象错误分类

以下分类只描述跨边界失败性质，不是业务错误码，也不定义传输状态映射。具体 Error Code 必须在获批责任范围内登记，且不能仅以分类名称代替。

| 抽象分类 | 稳定含义 | 不应混淆为 |
| --- | --- | --- |
| **契约或输入不满足** | 提供的信息在语法、类型、完整性或已声明约束上不符合契约 | 业务规则决定、身份判断或内部故障 |
| **身份或访问受限** | 无法建立所需身份上下文，或已建立主体不具备所需访问条件 | 对目标是否存在的确认；不得泄露安全策略细节 |
| **前置条件或状态冲突** | 请求所依赖的显式前置条件不成立，或观察到的状态与受控操作条件冲突 | 输入格式错误或未知内部故障 |
| **依赖不可用** | 完成操作所需的已授权依赖当前无法提供能力 | 业务拒绝或永久不支持；不得借此暴露内部拓扑 |
| **容量或暂时性限制** | 当前受控资源或执行额度不足以继续，但不声明具体恢复时间 | 永久失败或自动可重试承诺 |
| **时限或取消** | 操作因明确时限终止，或收到有效取消意图而停止 | 成功、回滚完成或底层原因已确定 |
| **完整性或一致性异常** | 检测到数据、契约或处理结果违反已声明的不变量 | 数据库设计结论或具体存储故障 |
| **不支持的能力** | 当前获批接口契约明确不支持所请求的能力或版本 | 暂时不可用或访问受限 |
| **内部未分类故障** | 责任边界确认失败，但不能安全、准确地公开更具体原因 | 可以忽略的错误；内部仍必须保留受控诊断与责任追踪 |

分类不决定是否重试、严重度、告警等级或用户文案。上述行为必须由具体错误语义和独立运维策略明确规定。

## 6. 责任分工

### 错误语义责任人

- 定义并维护 Error Code 的唯一语义、Category、Retry Guidance、安全披露和生命周期。
- 防止重复、冲突、复用或以新文案静默改变旧语义。
- 组织接口、架构、安全和测试评审，并维护使用方影响记录。

### 生产方

- 选择最准确且已登记的 Error Code，不以通用错误掩盖可安全表达的已知条件。
- 生成唯一 Error Occurrence ID，并提供完整必填字段。
- 在边界输出前完成敏感信息清理和关联标识合法性检查。
- 保存必要的受控内部诊断，但不把内部细节当作公共契约。

### 边界适配责任人

- 在不同接口边界之间转换错误时保持稳定语义和关联信息。
- 若目标边界只能表达更少信息，必须采用获批的安全收敛规则并记录可观测性影响。
- 任何协议状态映射都必须位于独立技术绑定契约中；本文不提供或暗示 HTTP/gRPC 映射。

### 接收方

- 只依据 Error Code、Category 和明确 Retry Guidance 采取程序化动作，不解析 Message 文案。
- 不把错误详情或关联 ID 当作认证、授权或目标存在性证明。
- 对未知 Error Code 采用安全、前向兼容的处理，并保留诊断关联。

### 评审与治理责任人

- 验证语义稳定性、分类准确性、最小披露、兼容性与 V2.3 架构一致性。
- 责任角色尚未指定时，由项目负责人书面指定；实现方不得自行假设审批权限。

## 7. 安全规则

- Message 与 Safe Details 必须默认安全，不得包含密钥、令牌、认证材料、个人信息、内部堆栈、源码位置、文件路径、查询内容、基础设施拓扑或供应商诊断。
- 身份或访问相关错误不得帮助未授权接收方判断目标是否存在、内部策略为何失败或需要何种凭据。
- Source、Request ID、Trace ID、Project ID、Asset ID、Job ID 只用于关联，不能建立信任或授权。
- Error Occurrence ID 必须不透明，不能编码敏感上下文。
- 面向外部边界的错误应遵循最小披露；详细原因保留在访问受控且有审计的内部诊断渠道。
- 不得将敏感信息隐藏在未声明字段、自由文本、嵌套原因或文档链接中。
- 安全清理不能改变 Error Code 的稳定语义；若只能安全地表达更宽泛语义，应使用已登记的安全收敛规则。

## 8. 生命周期与兼容性

每个具体 Error Code 应具有可审计的生命周期状态：

- **Proposed**：已提出但未获准使用。
- **Active**：已评审并允许生产方使用。
- **Deprecated**：不再允许新使用方采用，现有使用方处于受控迁移期。
- **Retired**：所有已知使用方已完成迁移；历史记录仍保留。

生命周期规则：

- 只有 Active Error Code 可以新增使用。
- 废弃时必须说明替代语义、影响范围、迁移期限和关闭证据。
- 已废弃或退役的 Error Code 不得复用。
- Error Code 语义、分类或恢复条件发生不兼容变化时，必须定义新的标识并完成变更评审。
- Message 文案变化不需要新 Error Code，但仍须满足安全和可理解性要求。
- 架构敏感变化遵守 [架构变更流程](../../governance/ARCHITECTURE_CHANGE_PROCESS.md)，不得通过错误码登记修改 V2.3 架构。

## 9. 明确不在本文范围内

本文不定义：

- HTTP 状态码、gRPC 状态或它们与 Error Code 的任何映射。
- 编程语言异常类型、堆栈结构或框架中间件。
- JSON、XML、Protocol Buffers 或其他序列化格式。
- 日志、指标、告警、重试器或追踪产品实现。
- 具体业务错误码、业务规则、业务文案或模块命名空间。
- 数据库表、错误持久化模型或查询结构。
- V2.3 架构之外的新服务、边界或依赖关系。

## 10. 错误语义登记检查清单

未来具体 Error Code 在进入 Active 状态前必须确认：

- 语义是否单一、稳定且未与既有标识重复？
- Category 是否准确且没有承担具体业务语义？
- 必填字段、条件字段和 Retry Guidance 是否明确？
- Message 与 Safe Details 是否符合最小披露和安全规则？
- 生产方、接收方、语义责任人及迁移责任是否明确？
- 未知错误、兼容性、废弃和安全收敛行为是否可验证？
- 是否完全避免 HTTP/gRPC 映射、业务错误码、数据库设计、技术选型或 V2.3 架构变更？

Phase 0 只建立本标准，不登记具体业务错误码或实现错误处理代码。
