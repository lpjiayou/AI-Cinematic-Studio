# AI Cinematic Studio 完成定义

## 1. 目的与适用范围

本文定义 ACS 工作项达到“完成”状态的统一最低标准，覆盖代码、测试、文档、审查和验收五类门禁。任何单项检查通过都不能替代完整完成定义。

本文适用于当前工程基础工作及未来经阶段授权的功能工作。**Phase 0 不允许开发业务功能**；当前使用“功能完成标准”时，应将其解释为对仓库、治理、架构文档或其他获准工程交付物的完成标准，不能据此创建业务代码、服务、数据库或依赖。

## 2. 强制完成条件

### 2.1 代码

适用于代码、配置、脚本和结构性工程资产；纯文档工作项应标记不适用并说明理由。

- 变更完整满足任务范围，不包含无关重构、临时实现或推测性扩展点。
- 实现符合 `architecture/` 权威文档、`ARCHITECTURE_GUARD.md` 和已接受 ADR。
- 代码结构、命名、错误处理和注释符合仓库约定，且不存在已知阻塞缺陷。
- 不包含凭据、生产数据、调试残留、生成物或仅适用于个人环境的文件。
- 新增依赖已获授权、版本可复现并完成许可证与安全评估。
- 构建、格式化和静态检查在适用范围内通过。
- 变更可回滚；若涉及迁移，已按获批 Migration Plan 执行。

Phase 0 额外要求：不得包含业务代码、服务实现、数据库表或持久化设计，也不得引入大型依赖或改变 V2.3 架构。

### 2.2 测试

- 为变更提供与风险相称的自动化测试或明确的人工验证方案。
- 单元、集成、契约和端到端测试放置在既定层级，不创建平行测试体系。
- 正常路径、关键边界和可预见失败路径均已覆盖；不适用项有书面依据。
- 测试可重复、结果确定，不依赖未声明的本地状态或真实生产资源。
- 所有适用测试与质量门禁通过，并保留可复核的执行结果。
- 未删除、跳过或弱化已有有效测试来规避失败。
- 缺陷修复包含能证明问题已被修复且防止回归的测试。

Phase 0 的测试仅验证目录、文档、规则和轻量工程基础，不创建业务测试、业务夹具或数据库测试。

### 2.3 文档

- README、架构、治理、接口或操作文档已按影响范围同步更新。
- 文档准确区分当前事实、已批准决策、提案与未来事项。
- 术语、文件路径、交叉引用和版本说明一致且可访问。
- 架构敏感变更关联 Accepted ADR，并同步更新受影响权威文档。
- 风险、限制、兼容性、迁移和回滚信息已在适用位置记录。
- 不适用的文档项已在工作项中说明原因。

### 2.4 审查

- 作者已完成自检，并提供目的、范围、验证证据、风险和回滚说明。
- 变更按 `CODE_REVIEW_RULES.md` 完成人工评审。
- 所有阻塞意见已解决；重要意见已解决或获得明确延期批准并建立跟踪项。
- 架构敏感变更已获得项目负责人、架构责任人及适用专项责任人批准。
- 批准后若发生实质性修改，已重新执行相关检查并重新请求评审。
- 分支和提交符合 `BRANCH_STRATEGY.md` 与 `COMMIT_CONVENTION.md`。

### 2.5 验收

- 每一条任务验收标准都有可复核证据，并由指定验收责任人确认。
- 交付范围与获批目标一致，明确记录未包含事项和后续事项。
- 已知风险已登记在 `RISK_REGISTER.md`，责任人和状态明确。
- 无未解决的阻塞缺陷、架构冲突、安全问题或合规问题。
- 发布、迁移、监控和回滚要求在适用时已准备并验证；不适用时有依据。
- 交付物可被目标使用方或维护者理解、验证和接续维护。
- 验收结论、日期和责任人已留存。

## 3. 不适用项处理

完成定义中的项目只有在客观上不适用时才可标记为 `N/A`。每个 `N/A` 必须记录原因并由评审者确认；不能用 `N/A` 绕过测试、文档、架构或安全门禁。

## 5. 不得标记完成的情形

存在以下任一情形时，工作项不得标记为完成：

- 验收标准未满足或缺少验证证据。
- 存在失败的强制检查或未解决的阻塞意见。
- 文档与实际状态不一致。
- 存在未经批准的架构、依赖、安全、数据或合规影响。
- 以“后续修复”为由接受当前范围内的必需工作缺失。
- Phase 0 交付物包含业务代码、服务实现、数据库设计、大型依赖或 V2.3 架构变更。
