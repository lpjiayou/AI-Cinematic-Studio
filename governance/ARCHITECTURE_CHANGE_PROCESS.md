# AI Cinematic Studio 架构变更流程

## 1. 目的与原则

本文定义 ACS 架构变更从识别、决策、实施到废弃的强制流程，确保变更经过明确授权、可追溯且可回滚。本流程不得用于臆造未来模块，不能以治理文件替代或改变 V2.3 已批准架构。

基本原则：

- 决策先于实现；`Proposed` ADR 不构成实施许可。
- 事实、提案和决策必须明确区分。
- 实施范围不得超过获批决策范围。
- 旧设计必须有受控退出过程，不得静默删除或覆盖历史。
- Phase 0 禁止业务代码、服务实现、数据库设计和大型依赖。

## 2. 何时必须创建 ADR

出现以下任一情况时，必须创建 ADR：

- 新增、删除、拆分、合并或改变系统层级与模块职责。
- 改变依赖方向、公共能力归属或跨边界协作方式。
- 新增或修改公共接口、协议、事件、兼容性策略或错误语义。
- 改变运行时、部署单元、计算边界、基础设施拓扑或全仓库技术栈。
- 改变数据所有权、持久化边界、数据生命周期或安全信任边界。
- 引入会形成长期约束、较高迁移成本或广泛传递影响的依赖。
- 偏离 `architecture/` 下的权威文档或现有 Accepted ADR。
- 废弃或替代现有架构设计。
- 对某项变更是否属于架构变更存在合理争议或不确定性。

通常不需要 ADR 的事项包括：不改变架构语义的错别字修正、链接修复、格式统一和已批准设计范围内的等价实现细节。但此类变更仍须遵守评审和完成标准；一旦影响边界或约束，立即转入 ADR 流程。

## 3. 角色与审批责任

### 提案人

- 使用 `ADR_TEMPLATE.md` 完整描述 Context、Decision、Alternatives、Consequences 和 Migration Plan。
- 提供可验证事实、影响分析、风险与回滚方案。
- 在获批前不得实施或通过目录、依赖和命名预占未来架构。

### 项目负责人

- 确认变更符合当前阶段、项目目标和治理范围。
- 指定架构责任人及必要的专项责任人。
- 对范围、优先级、资源与最终实施授权负责。

### 架构责任人

- 验证变更与 V2.3 架构、层级边界、职责矩阵和依赖规则一致。
- 评估候选方案、长期约束、迁移成本和架构风险。
- 对架构结论给出明确批准或拒绝意见。

### 专项责任人

涉及安全、接口、测试、基础设施、可观测性或发布治理时，由对应责任人评审其专业影响。正式责任体系尚未建立时，项目负责人必须在 ADR 中书面指定，不能由提案人自行假设。

### 审批要求

- ADR 至少需要项目负责人和架构责任人共同批准。
- 涉及专项治理边界时，还必须获得对应专项责任人批准。
- 提案人不能代替必需审批人批准自己的提案。
- 任一必需审批人为“拒绝”或存在未解决的阻塞意见时，状态不得设为 `Accepted`。

## 4. 架构变更标准流程

### 步骤 1：识别与分类

1. 关联明确任务、风险或架构问题。
2. 对照第 2 节判断是否需要 ADR。
3. 明确当前事实、范围、不变约束和 Phase 0 边界。

产出：问题说明；需要 ADR 时分配唯一 ADR ID，状态为 `Proposed`。

### 步骤 2：形成提案

1. 按模板填写所有必填字段。
2. 至少比较真实候选方案与保持现状方案。
3. 分析对架构文档、依赖、接口、安全、测试、运维和发布的影响。
4. 建立风险登记关联，并定义迁移、验证和回滚条件。

产出：可评审的 Proposed ADR。此阶段禁止提前实现。

### 步骤 3：评审与决策

1. 项目负责人确认范围及阶段合规性。
2. 架构责任人完成架构一致性评审。
3. 必要的专项责任人完成专业评审。
4. 提案人解决阻塞意见并记录重要取舍。
5. 审批人作出 `Accepted` 或 `Rejected` 结论。

产出：带审批记录的 ADR。只有 `Accepted` 状态可进入实施。

### 步骤 4：受控实施

1. 将变更拆分为可独立验证、可回滚的工作项。
2. 严格按 ADR 的 Decision 和 Migration Plan 实施。
3. 同步更新受影响的权威架构文档、责任矩阵和依赖规则。
4. 增加与风险相称的测试、检查或人工验证证据。
5. 按 `CODE_REVIEW_RULES.md` 完成评审，并按 `DEFINITION_OF_DONE.md` 验收。

若实施中发现必须扩大范围、改变核心取舍或无法满足回滚条件，应停止实施，修订或新建 ADR 并重新审批。

### 步骤 5：验证与关闭

1. 验证实际结果与 ADR 决策一致。
2. 确认迁移完成、旧路径受控退出且文档无冲突。
3. 更新关联风险状态和验证证据。
4. 记录复核日期及后续事项。

ADR 保持 `Accepted`，实施工作项按完成标准关闭；ADR 本身不能因实施完成而删除。

## 5. 如何修改已批准架构

- 仅修改措辞、链接或不改变语义的勘误，可保留原 ADR，并在变更历史中记录修改内容、作者和日期。
- 改变 Decision、适用范围、核心约束、后果或迁移策略时，必须创建新 ADR，不得直接重写原决策。
- 新 ADR 必须引用原 ADR，解释变化原因和兼容影响，并重新完成全部审批。
- 新决策获批前，旧 Accepted ADR 继续有效。
- 不允许通过修改代码、测试、目录或配置形成与权威架构不一致的事实标准。

## 6. 如何废弃或替代旧设计

1. 创建新 ADR，说明废弃原因、目标状态、影响资产和迁移计划。
2. 评估现有使用方、兼容窗口、风险、验证和回滚条件。
3. 取得与原设计同等级或更高等级的审批。
4. 新 ADR 获批后，将旧 ADR 标记为 `Deprecated` 或 `Superseded`：
   - `Deprecated`：仍在受控使用或迁移期，不再允许新采用。
   - `Superseded`：已由新 ADR 完整替代。
5. 在新旧 ADR 中建立双向引用，保留原始内容和审批历史。
6. 按迁移计划更新权威文档；过渡期文档必须明确当前有效规则。
7. 完成验证后关闭迁移工作项和关联风险，不删除旧 ADR。

禁止在没有替代决策、影响评估和迁移证据的情况下静默废弃旧设计。

## 7. 紧急与例外处理

架构治理例外必须记录原因、责任人、范围、风险、补偿控制、到期时间和退出计划。紧急情况可以缩短评审等待时间，但不能取消项目负责人和架构责任人的明确审批，也不能突破 Phase 0 禁令。

## 8. Phase 0 执行边界

当前 Phase 0 中，本流程只用于记录和保护工程基础架构。任何 ADR 都不得授权：

- 业务代码或业务功能。
- 服务实现或运行时业务组件。
- 数据库表、字段、迁移或持久化设计。
- 大型依赖或为未来设想预装的技术栈。
- 对 V2.3 架构的未经授权修改。

超出边界的提案应保持 `Proposed` 或标记为 `Rejected`，等待后续阶段获得明确授权。
