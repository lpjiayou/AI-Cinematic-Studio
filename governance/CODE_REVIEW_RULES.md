# AI Cinematic Studio 代码评审规则

## 1. 目标

代码评审用于验证变更的正确性、边界合规性、可维护性、安全性和可追溯性。评审不是形式化签字，也不能替代作者的自检和自动化验证。

本文所称“代码评审”覆盖代码、配置、文档、测试、脚本和基础设施变更。

## 2. Phase 0 专项审查

ACS-P0-001 及其他 Phase 0 变更必须首先确认：

- 不包含任何业务功能、业务占位实现或业务示例。
- 不包含数据库、数据表、ORM、迁移或持久化设计。
- 未安装大型依赖或为未来设想预装工具链。
- 未臆造、调整或替代未来模块架构。
- 变更仅服务于工程基础、治理和文档完整性。

任一项不满足即为阻塞问题，不能通过“后续再清理”接受。

## 3. 角色与职责

### 作者

- 保证变更范围清晰、提交可读并完成自检。
- 在评审说明中陈述目的、范围、验证证据、风险和已知限制。
- 主动标出架构、依赖、安全、数据或兼容性影响。
- 响应全部意见；不能仅通过关闭讨论来视为已解决。

### 评审者

- 独立验证变更是否满足任务和架构约束。
- 聚焦正确性、风险和长期维护成本，避免无关的个人风格争论。
- 清楚区分阻塞意见、建议和问题。
- 对无法确认的领域请求具备相应职责的评审者参与。

### 合并责任人

- 确认所需批准、检查和讨论均已完成。
- 确认合并目标、提交策略和分支状态正确。
- 不得在阻塞意见未解决时强制合并。

作者与评审者原则上不能是同一人。涉及架构边界、安全策略或全仓库治理的高影响变更，应获得对应责任人的批准；责任体系尚未建立时，由项目负责人明确指定。

## 4. 评审请求最低信息

每个评审请求至少包含：

- 关联任务或决策记录。
- 变更目的与不在范围内的事项。
- 关键文件和行为变化摘要。
- 验证方式及结果。
- 风险、兼容性、回滚方式和后续事项；不适用时应明确说明。
- 架构、依赖、安全、数据、接口和运维影响声明。

纯文档变更也必须说明权威来源及其与现有规范的一致性。

## 5. 规模与可评审性

- 评审请求应围绕单一目标，避免混合重构、格式化和功能变更。
- 大型变更应按可独立验证的步骤拆分，但不得通过拆分规避整体架构评审。
- 机械生成或批量格式化的内容应与语义变更分开。
- 临时文件、构建产物、编辑器状态和无关锁文件变化不得进入评审。

## 6. 评审检查清单

评审者应按适用性检查：

### 范围与正确性

- 变更是否完整满足任务和验收标准。
- 是否存在越界实现、隐藏副作用或不必要的预留。
- 错误处理、边界情况和失败模式是否清晰。

### 架构与依赖

- 是否符合 `architecture/` 下的分层、职责和依赖规则。
- 是否引入反向依赖、循环依赖、跨层捷径或职责泄漏。
- 新依赖是否必要、轻量、可审计且经过授权。
- 是否通过目录或命名隐式定义了未经批准的未来模块。

### 测试与验证

- 验证证据是否与风险匹配且可重复。
- 测试层级和位置是否正确。
- 是否存在被删除、跳过、削弱或掩盖的有效检查。

### 安全与合规

- 是否包含凭据、敏感数据、危险默认值或不可信输入风险。
- 第三方依赖和内容是否满足许可证及合规要求。
- 权限、日志和错误信息是否遵循最小披露原则。

### 可维护性与文档

- 命名、结构和说明是否清晰且与仓库术语一致。
- 复杂度和抽象是否与当前需求相称。
- 文档是否同步，陈述是否区分当前事实与未来提案。

## 7. 意见分级

评审意见使用以下级别：

- **阻塞（Blocking）**：正确性、安全、架构、数据完整性、合规或任务范围问题；必须解决后才能合并。
- **重要（Major）**：显著影响维护性、验证充分性或长期成本；原则上应在本次变更解决，延期需明确批准和跟踪事项。
- **建议（Suggestion）**：不影响合并的改进建议，应说明收益。
- **问题（Question）**：需要澄清意图或依据；若澄清暴露风险，可升级为阻塞或重要意见。

意见应指向具体位置，描述风险，并在可能时提出可验证的修改方向。

## 8. 批准与重新评审

- 所有阻塞意见必须由提出者或具备同等职责的评审者确认解决。
- 作者在批准后追加实质性变更时，必须重新请求评审和执行相关检查。
- 自动化检查通过不等同于人工批准；人工批准也不能覆盖失败的强制检查。
- 未经批准的架构变化不能通过多数同意替代正式决策流程。

## 9. 合并后责任

若合并后发现高风险问题，应优先恢复稳定状态并记录原因。后续修复必须保留与原评审请求的可追溯关系；禁止静默修改历史以掩盖问题。
