# AI Cinematic Studio 分支策略

## 1. 策略目标

ACS 采用以受保护主分支和短生命周期工作分支为核心的开发方式，以减少长期分叉、降低集成风险并保持可追溯性。本策略只定义协作规则，不预设未来业务模块、发布节奏或部署拓扑。

## 2. 长期分支

### `main`

`main` 是唯一默认长期分支，代表已评审、可复现且满足当前阶段质量门槛的仓库状态。

`main` 应启用以下保护：

- 禁止直接推送和强制推送。
- 变更必须通过评审请求合并。
- 必须通过已配置的强制检查。
- 必须解决所有阻塞评审意见。
- 禁止删除或改写已共享历史。

在发布体系尚未正式确定前，不创建长期 `develop`、环境分支或版本分支。确有需要时，应通过独立治理决策引入，不得由单个任务自行建立。

## 3. 工作分支命名

工作分支使用小写、短横线分隔，并尽可能包含任务编号：

```text
<type>/<task-id>-<short-description>
```

允许的基础类型：

- `foundation/`：仓库与工程基础。
- `docs/`：文档变更。
- `governance/`：治理规则变更。
- `test/`：测试基础或测试修正。
- `fix/`：缺陷修复。
- `chore/`：不改变产品行为的维护工作。

示例：

```text
foundation/acs-p0-001-repository-initialization
docs/acs-p0-002-architecture-clarification
```

分支类型不构成架构模块定义。新增类型应基于稳定的工作分类，而非未经批准的产品或模块设想。

## 4. 分支生命周期

1. 从最新的 `main` 创建工作分支。
2. 仅提交当前任务所需变更，定期同步 `main` 以尽早发现冲突。
3. 发起评审请求，完成强制检查与批准。
4. 使用仓库统一采用的合并方式并确保提交信息符合约定。
5. 合并后删除工作分支，不重复用于其他任务。

工作分支应保持短生命周期。若任务长期未完成，应拆分可独立评审的基础变更，而不是将分支作为永久集成区。

## 5. 合并与历史管理

- 默认优先采用能够保持 `main` 历史清晰的合并方式；具体方式由仓库配置统一执行。
- 不在共享分支上执行破坏性历史重写。
- 变基仅用于整理个人未共享的工作历史，或在团队明确协调后进行。
- 合并提交或压缩后的提交信息必须保留任务编号与变更意图。
- 冲突解决后应重新执行受影响的检查，不得仅以“可合并”为完成依据。

## 6. 紧急修复

紧急修复仍从 `main` 创建短生命周期 `fix/` 分支，并遵守评审、验证和可追溯要求。只有已批准的应急流程可以缩短等待时间，不能取消安全、架构或范围审查。

在 Phase 0 不预建热修复分支、发布分支或生产环境流程。

## 7. Phase 0 限制

Phase 0 分支中的内容仅限工程仓库基础。禁止：

- 提交业务功能或业务占位代码。
- 提交数据库设计或持久化实现。
- 通过分支命名或目录变更定义未来模块架构。
- 引入大型依赖或未经批准的工具链。
- 创建没有当前治理用途的长期分支。

## 8. 例外与审计

分支保护例外、强制合并或历史修复必须由项目负责人明确批准并记录原因、影响范围和补救措施。任何例外都不得成为后续常规操作的默认先例。
