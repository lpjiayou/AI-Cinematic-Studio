# AI Cinematic Studio 开发规则

## 1. 目的与适用范围

本文定义 AI Cinematic Studio（以下简称 ACS）工程活动的最低治理要求，适用于仓库内的代码、配置、文档、测试、脚本与基础设施变更。规则服务于长期可维护、可审计和可扩展的企业级工程建设，不替代经正式评审通过的架构决策。

当本文与已批准的架构规范冲突时，应停止实现并发起澄清；任何人不得通过提交代码、目录或依赖关系隐式改写架构。

## 2. Phase 0 强制边界

当前阶段为 **Phase 0 Engineering Foundation Initialization**。本阶段只允许建立仓库结构、工程治理、基础文档与必要的轻量验证能力。

以下事项明确禁止：

- 开发、占位或模拟任何业务功能，包括 API、页面、工作流、领域服务和商业化逻辑。
- 设计数据库、数据表、字段、索引、迁移、ORM 模型或持久化方案。
- 安装大型依赖、完整业务框架、数据库组件、消息系统或仅为未来设想准备的工具链。
- 臆造、重命名、拆分、合并或调整任何未来模块及其架构职责。
- 以“临时实现”“示例代码”或“预留目录”为由绕过上述限制。

如工作项超出上述范围，必须暂停并由项目负责人确认后进入后续阶段，不能在 Phase 0 提交中夹带实现。

## 3. 变更原则

所有变更必须遵循以下原则：

1. **任务驱动**：每项变更应对应明确的任务、问题或经批准的工程目标。
2. **最小范围**：只修改完成当前目标所需的内容，不顺带重构或预建未来能力。
3. **边界清晰**：遵守 `architecture/` 中已批准的分层、职责和依赖规则。
4. **可验证**：提供与风险相称的检查、测试或人工验证证据。
5. **可回滚**：避免将互不相关的变更混入同一提交；提交应可独立理解和撤销。
6. **文档同步**：行为、接口或治理规则发生获批变更时，同步更新权威文档。
7. **默认安全**：不得提交密钥、令牌、个人信息、生产数据或其他敏感信息。

## 4. 开发工作流

开始工作前：

- 阅读任务范围、验收标准及相关架构和治理文档。
- 检查工作区状态，识别并保留他人的未提交变更。
- 判断变更是否涉及架构边界、依赖、接口契约、安全或数据；如涉及，先取得所需批准。

实施过程中：

- 使用项目既有约定，不创建重复规范或平行目录体系。
- 保持实现与业务无关，除非任务所在阶段明确授权业务开发。
- 不使用空壳业务代码、无明确用途的抽象或推测性扩展点。
- 对非显然的工程决策记录原因、约束和取舍，而不只记录结果。

提交前：

- 执行适用的格式、静态检查、测试与文档链接检查。
- 确认没有生成物、临时文件、凭据或无关变更进入提交。
- 按 `COMMIT_CONVENTION.md` 组织提交，并按 `CODE_REVIEW_RULES.md` 发起评审。

## 5. 依赖管理

- 新增依赖必须有当前任务中的明确用途，不得为未经批准的未来能力预装。
- 优先使用标准库、仓库现有能力或小型且职责单一的工具。
- 引入依赖前应评估许可证、维护活跃度、安全记录、体积、传递依赖和锁定风险。
- 依赖版本应可复现；禁止使用无界版本或来源不明的二进制文件。
- 大型依赖或影响全仓库的工具链变更必须单独提案和评审；Phase 0 不予引入。

## 6. 质量与测试要求

- 测试层级使用 `tests/unit`、`tests/integration`、`tests/contract` 与 `tests/e2e` 的既定分类，不自行发明平行分类。
- 测试必须确定、可重复，不能依赖未声明的本地状态或真实生产资源。
- 缺陷修复应在适用阶段附带能够复现缺陷的测试；纯文档或目录变更可使用结构与内容检查作为验证证据。
- 不得通过删除、跳过或放宽有效检查来使变更通过。
- Phase 0 的验证仅限仓库基础与治理完整性，不创建业务测试或业务夹具。

## 7. 文档与可追溯性

- 文档使用清晰、可执行、可验证的表述，区分已批准事实、约束、建议与待决事项。
- 不将讨论稿描述为最终架构，不将未来设想写成当前能力。
- 影响架构规则的变更必须同时更新对应权威文档，并在评审中说明影响范围。
- 链接、文件名和术语应保持一致；废弃内容需说明替代项与迁移方式。

## 8. 安全与合规基线

- 所有配置示例使用无效占位值；禁止以任何形式提交真实凭据。
- 第三方内容、数据与依赖必须满足适用许可证和组织合规要求。
- 日志、测试数据和文档不得暴露个人信息或内部敏感信息。
- 发现凭据泄露或高风险安全问题时，应立即停止常规流程并按安全事件流程升级。

## 9. 完成定义

一项变更只有同时满足以下条件才可视为完成：

- 任务范围和验收标准全部满足。
- 适用检查通过并留有可复核证据。
- 文档、测试与实现保持一致。
- 未产生未经批准的架构、依赖、数据或安全影响。
- 已完成所需评审，所有阻塞意见均已解决。
- 提交历史清晰且不包含无关内容。

## 10. 例外处理

任何例外必须在实施前获得明确批准，并记录原因、风险、适用范围、责任人和终止条件。紧急情况不得成为长期绕过规则的依据；临时例外应设置修复任务并在约定期限内关闭。
