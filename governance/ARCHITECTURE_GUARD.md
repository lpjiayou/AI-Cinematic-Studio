# AI Cinematic Studio 架构守卫

## 1. 目的

架构守卫用于防止实现、目录、依赖或临时决策侵蚀已批准的系统边界。它定义架构合规的检查与变更机制，不在本文中设计产品功能、数据库或未来模块架构。

架构权威信息以 `architecture/` 下经批准的文档及正式架构决策为准。治理文档负责约束过程，不能替代架构事实。

## 2. 基本原则

- **显式边界**：层级、模块职责和依赖方向必须由已批准文档定义。
- **依赖单向**：不得通过导入、调用、配置、脚本或共享状态绕过依赖规则。
- **职责唯一**：不得因开发便利将职责复制到多个位置或建立隐性共享模块。
- **接口优先**：跨边界协作必须遵循获批接口契约，不依赖内部实现细节。
- **变更先决策**：架构变更必须先完成提案与批准，再进入实现。
- **最小机制**：只引入满足当前阶段需求的结构和工具，不为假设性未来提前建设。

## 3. Phase 0 架构冻结边界

Phase 0 只建立工程基础，不授权任何业务架构实现。以下行为均被禁止：

- 创建业务服务、应用、领域模型、处理流程或占位实现。
- 开发任何业务功能、业务示例或业务占位代码。
- 设计数据库、存储模型、表结构、迁移方案或数据访问层。
- 安装大型依赖，包括大型框架、数据库、消息系统、工作流引擎或其他未来运行时组件。
- 臆造未来模块名称、职责、接口、层次或部署关系。
- 修改、替换或通过目录结构暗示未来模块架构。
- 将讨论中的设想描述为 V2.3 最终架构事实。

空的顶层工程目录只表示仓库组织入口，不自动产生模块、服务或产品职责。

## 4. 受保护的架构维度

任何涉及以下维度的变更均视为架构敏感变更：

- 系统层级、边界及依赖方向。
- 模块职责、所有权或公共能力归属。
- 跨模块接口、事件、协议或兼容性策略。
- 运行时、部署单元、计算边界或基础设施拓扑。
- 数据所有权、持久化边界或数据生命周期。
- 身份、权限、信任边界和安全控制。
- 全仓库依赖、构建、测试或发布机制。

架构敏感不代表禁止演进，但必须执行更严格的决策和评审流程。

## 5. 禁止的依赖模式

在任何阶段，除非权威架构明确允许，禁止：

- 逆向依赖、循环依赖和跨层直接访问。
- 通过相对路径、构建别名或动态加载隐藏真实依赖。
- 通过共享数据库、共享可变状态或内部配置形成隐式耦合。
- 从其他边界复制内部模型并使其成为事实接口。
- 将通用包作为逃避职责归属的“杂物箱”。
- 由测试、脚本或基础设施代码反向承载业务职责。

实际依赖关系应可被静态检查、构建配置或清晰文档识别。

## 6. 架构变更流程

架构敏感变更必须遵守 [架构变更流程](ARCHITECTURE_CHANGE_PROCESS.md)，并按顺序完成：

1. 描述问题、现状和不变约束。
2. 提出候选方案、影响范围、取舍、风险和回滚路径。
3. 标明对层级、职责、接口、数据、安全、测试和运维的影响。
4. 由项目负责人和相应架构责任人完成明确批准。
5. 更新相关权威架构文档和可追溯决策记录。
6. 在批准后实施，并增加适用的自动化守卫或验证。

未决提案不得通过代码、目录、依赖或命名提前落地。责任人或决策记录机制尚未建立时，应暂停变更并由项目负责人指定，不得自行假设。

## 7. 评审门禁

每个变更应回答以下问题：

- 是否改变层级、职责、依赖方向或公共接口？
- 是否新增跨边界调用、共享状态或运行时依赖？
- 是否涉及数据所有权、安全边界、部署或可观测性？
- 是否与 `system-overview.md`、`layer-boundaries.md`、`module-responsibility-matrix.md` 或 `dependency-rules.md` 冲突？
- 是否引入尚未批准的模块、名称或未来能力？

任一回答为“是”或“不确定”时，必须标记为架构敏感并请求专项评审。不能以自动化检查通过替代架构批准。

## 8. 自动化守卫演进

可在后续获批阶段逐步加入：

- 依赖方向和循环依赖检查。
- 目录边界、公开接口和包可见性检查。
- 架构文档链接与责任矩阵一致性检查。
- 禁止依赖、许可证和安全策略检查。
- 架构契约测试和变更影响报告。

这些能力必须依据已批准架构配置。Phase 0 不安装大型工具，也不编写业务相关架构测试。

## 9. 偏差与例外

发现架构偏差时，应停止扩大影响，记录事实并选择修复或正式提案。例外必须包含批准人、理由、范围、风险、补偿控制、到期时间和退出计划。

临时例外不能自动转化为架构先例；到期后未重新批准的例外视为不合规。

## 10. 合规完成条件

架构相关变更只有在以下条件全部满足时才可合并：

- 与权威架构文档一致，或对应架构变更已正式批准。
- 依赖关系清晰、可审计且无禁止模式。
- 受影响文档、检查和责任矩阵已同步。
- 风险、迁移和回滚方式已说明。
- 所有架构阻塞意见已解决。
