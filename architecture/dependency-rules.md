# 依赖规则

## 1. 目标

本规则用于保持仓库依赖可理解、可替换和可自动检查。它约束源代码、配置、测试、脚本和文档之间的方向，但不选择具体语言、框架或构建工具。

## 2. 基本原则

1. 所有跨边界依赖必须指向公开、版本化或明确声明的契约。
2. 禁止通过相对路径、复制内部代码或共享数据库等方式绕过公开边界。
3. 生产依赖保持单向，任何循环依赖都必须在合并前消除。
4. 依赖方向不等于数据流方向；回调、事件或响应仍需遵守契约边界。
5. 未经任务批准，不得引入新的运行时依赖、服务依赖或基础设施耦合。

## 3. 仓库级允许关系

| 来源 | 可以依赖 | 不得依赖 |
| --- | --- | --- |
| `apps/` | 已批准的公开服务契约、稳定共享包、应用内部资产 | 服务内部实现、其他应用内部实现、基础设施私有细节 |
| `services/` | 稳定共享包、自身内部资产、其他服务的公开契约 | 其他服务内部实现、应用实现、部署目录作为运行时库 |
| `packages/` | 更底层且无业务专属语义的共享包 | `apps/`、`services/`、`infrastructure/` 的具体实现 |
| `infrastructure/` | 公开的部署/构建契约和声明输入 | 业务内部实现、测试代码作为生产依赖 |
| `scripts/` | 完成工程操作所需的公开工具入口 | 私有业务实现、未经声明的生产资源 |
| `tests/` | 被测公开资产及明确测试支持资产 | 生产机密、不可控生产数据 |

“可以依赖”不代表自动批准。具体依赖仍需属于当前任务范围、具备所有者，并通过代码评审。

## 4. 明确禁止的耦合

- 应用或服务直接读取另一个边界的私有文件；
- 多个服务通过未声明的数据库结构形成隐式契约；
- 以 `packages/` 为名放置业务流程，从而绕过服务或应用边界；
- 让 `infrastructure/` 或 `scripts/` 成为业务逻辑的唯一实现位置；
- 生产代码依赖 `tests/`、测试夹具或测试专属配置；
- 文档中声明一条与强制架构基线冲突但未审批的依赖；
- 为尚未批准的未来模块预先添加依赖或技术栈。

## 5. 第三方依赖

引入第三方依赖前必须记录用途、直接消费者、许可证与安全影响、版本策略、替代方案以及移除成本。大型依赖或基础框架必须由独立任务批准；ACS-P0-001 不安装任何依赖。

依赖应固定在可复现的版本范围内，由所属边界显式声明。禁止仅因开发便利将工具性依赖加入生产运行时。

## 6. 测试与工程依赖

- 单元测试保持隔离与确定性；
- 集成测试仅连接明确列出的受控组件；
- 契约测试验证公开边界，不复制对方内部行为；
- 端到端测试通过正式入口验证关键路径；
- 脚本通过公开命令或契约编排工程操作，不直接修改业务内部状态。

## 7. 守卫与例外

当前阶段以评审清单和目录责任矩阵执行规则。技术栈获批后，应逐步增加静态依赖图、禁止导入规则、循环检测和契约兼容性检查。

临时例外必须包含责任人、原因、影响范围、到期条件和消除计划，并经架构评审批准。永久改变依赖方向的提案必须更新架构基线，不能作为“临时例外”长期存在。
