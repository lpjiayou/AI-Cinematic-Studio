# 层级依赖图

## 1. 目的

本文档对 V2.3 高层系统视图中的生产依赖方向作出可审查约束。它补充仓库级 [依赖规则](dependency-rules.md)，不替代该文件，也不批准任何具体模块、接口、第三方依赖或技术实现。

## 2. 读图约定

记号 `A → B` 表示 A 可以在具体依赖另行获批后，通过 B 的公开契约依赖 B。该记号不表示调用一定同步发生，也不表示数据、事件或响应只能沿同一方向流动。

允许方向不是自动授权，也不证明对应实现已经存在。每一项实际依赖仍必须具有明确消费者、稳定公开契约、所属任务、责任人和验证证据。

## 3. 允许的直接依赖

| 依赖方 | 可进入评审的相邻下层方向 | 必须满足的边界 |
| --- | --- | --- |
| Application Layer | V5 Core OS | 只使用 V5 Core OS 公开契约 |
| V5 Core OS | V4 Platform | 只使用 V4 Platform 公开契约 |
| V4 Platform | V3 Render Core | 只使用 V3 Render Core 公开契约 |
| V3 Render Core | Compute | 只使用 Compute 公开契约 |
| Compute | Foundation | 只使用 Foundation 公开契约 |
| Foundation | 无 | 不依赖任何上层 |

由此形成标准的高层依赖治理次序：

`Application Layer → V5 Core OS → V4 Platform → V3 Render Core → Compute → Foundation`

层内依赖不因本表而自动获批；其合法性应由 V2.3 既有模块定义或后续独立、获批的责任与契约记录判断。

## 4. 禁止的依赖

### 4.1 反向依赖

任何下层依赖上层的关系均被禁止，包括但不限于 V4 Platform 依赖 V5 Core OS、Compute 依赖 V3 Render Core、Foundation 依赖任一上层。依赖倒置只能通过由下层拥有或认可的稳定公开抽象实现，不能让下层导入上层实现。

### 4.2 跨层依赖

禁止跳过相邻层直接建立生产依赖，例如 Application Layer 直接依赖 V4 Platform、V3 Render Core、Compute 或 Foundation，V5 Core OS 直接依赖 V3 Render Core 或更下层。需要深层能力时，应由各相邻层通过自己的公开边界逐层承接。

### 4.3 循环依赖

禁止层级之间以及具体实现形成直接或间接循环。循环不得通过运行时注入、共享配置、公共目录、事件回调、复制实现或共享持久化状态进行隐藏。

### 4.4 边界绕过

以下做法不构成合法依赖：

- 导入另一层的私有实现或内部文件；
- 依靠未声明的共享状态、共享存储结构或环境副作用；
- 将上层语义下沉到 Foundation、Compute 或通用资产中以规避方向限制；
- 用测试、脚本或基础设施配置作为生产运行时的跨层通道；
- 先实施依赖，再以补充文档方式追认。

## 5. 与其他依赖视图的关系

本图约束 Application Layer、V5 Core OS、V4 Platform、V3 Render Core、Compute、Foundation 的逻辑层依赖。仓库路径之间的依赖继续由 [依赖规则](dependency-rules.md) 与 [层级边界](layer-boundaries.md) 约束。逻辑层和仓库路径是不同视图；未获批准的映射不得用于推导例外。

若不同规则看似冲突，应采用更严格的约束并暂停合并，直至架构评审明确唯一有效的边界。

## 6. 例外流程

确需偏离标准依赖链时，必须在实现或合并前按照 [架构变更流程](../governance/ARCHITECTURE_CHANGE_PROCESS.md) 提交 ADR 或独立例外记录，至少包含：

1. 关联任务、申请人、责任人和评审人；
2. 请求的来源层、目标层、依赖类型与公开契约；
3. 无法采用标准相邻层路径的证据及已评估替代方案；
4. 对 V2.3 基线、测试、安全、可观测性和维护性的影响；
5. 适用范围、开始条件、到期日期或明确到期事件；
6. 隔离措施、监测方式、移除计划、迁移方案与回滚条件。

例外必须经过架构评审明确批准并可追溯。口头同意、代码已经存在、交付期限或工具限制均不能自动构成例外。

临时例外不得无限期续期或扩大适用范围；到期前必须移除，或作为永久架构变更重新评审。永久改变依赖方向的决定必须更新 V2.3 架构基线及所有相关规则，不能长期以例外形式存在。

## 7. 守卫方式

当前阶段通过架构评审、责任矩阵和变更清单执行本图。技术栈确定后，可以在独立获批任务中加入静态依赖检查、禁止导入规则和循环检测；在这些自动化能力实际落地前，不得声称已经由工具强制执行。
